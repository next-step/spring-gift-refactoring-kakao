# 선물하기 리팩터링 미션 회고

## 미션 개요

카카오 선물하기 레거시 코드를 리팩터링하는 미션이었다. 1단계에서는 구조 변경(서비스 추출), 2단계에서는 작동 변경(트랜잭션, 누락 작동)과 도메인 책임 되찾기를 진행했다. Claude Code를 활용해서 작업했다.

---

## 1단계: 리팩터링 준비하기

### 무엇을 했는가

스타일 정리 → 불필요 코드 제거 → 서비스 계층 추출 순서로 진행했다. Controller에 몰려있던 비즈니스 로직을 9개 Service로 분리하고, 81개 테스트를 추가했다. 구조만 바꾸고 작동은 바꾸지 않는 것이 원칙이었기 때문에 `@Transactional`은 의도적으로 붙이지 않았다.

### 리뷰 내용

리뷰어에게 총 9개 코멘트를 받았다.

- **불필요 코드 제거 순서**: "스타일 정리보다 불필요 코드 제거가 먼저 아닌가요?" — 맞는 말이다. 삭제할 코드에 스타일을 정리할 이유가 없으니까. 다음에는 불필요 코드 제거를 먼저 하겠다고 답했다.
- **`@Transactional` 미적용**: 구현 전략을 잘 지켜줬다는 긍정적 피드백. 트랜잭션 추가도 작동 변경이니 분리한 판단이 맞았다.
- **e2e 테스트 부재**: "리팩터링 안전망으로 e2e 테스트가 있었으면 더 좋지 않았을까?" — `@WebMvcTest` 기반 단위 테스트만 작성했는데, `@SpringBootTest`로 실제 DB를 쓰는 e2e 테스트가 있었으면 구조 변경 전후로 외부 동작이 동일한지 더 확실하게 검증할 수 있었을 것이다.
- **도메인별 패키지 구조**: 현재 구조에 대해 어떻게 생각하는지 질문. `OrderService`가 `OptionRepository`, `MemberRepository`를 직접 참조해서 패키지 경계가 모호하다는 점을 인지하고 있다고 답했다.
- **getter 대신 객체에 메시지 전달**: `member.getPassword()`로 꺼내서 비교하지 말고 `member.matchesPassword()`로 바꿔보라는 피드백. 2단계 Tell Don't Ask 적용의 시작점이 됐다.
- **DTO/Entity 반환 혼재**: Service마다 DTO를 반환하는 곳과 Entity를 반환하는 곳이 섞여있다는 지적. Service는 Entity만 반환하고 Controller에서 DTO 변환하도록 통일했다.
- **`validateProductExists` 네이밍**: 실제로는 Product를 가져오는 건데 validate라는 이름이 어색하다. `getProduct()`로 수정했다.
- **Exception ignored**: 카카오 알림 실패 시 예외를 완전히 삼키고 있었다. `log.warn()`으로 수정했다.
- **`ResponseEntity<?>` 와일드카드**: 리팩터링 전 코드를 그대로 둔 건데, 타입을 명시하는 게 맞다.

### 리뷰 반영

리뷰 받은 항목 중 코드 수정이 필요한 5개(matchesPassword, Entity 반환 통일, getProduct 네이밍, log.warn, 와일드카드 제거)를 반영해서 재제출했다.

## 수업 피드백

리뷰와 별개로 수업에서 받은 피드백도 있었다.

- **구조 변경과 작동 변경을 섞으면 리뷰가 어려워진다.** 코드를 작성하는 사람은 편하지만 리뷰하는 사람은 분석/입증하기 어렵다.
- **리뷰 가능성은 설계 품질의 지표다.** 리뷰할 수 없는 PR을 만들면 팀은 유지보수를 포기하게 된다.
- **AI는 책임을 지지 않는다.** AI가 코드 잘못 짜면 우리가 욕먹는다. 변경의 책임은 여전히 인간에게 있다.
- **좋은 아키텍트는 정치를 잘해야 한다.** 리팩터링을 동료에게 납득시키는 과정이 필요하다. 논리적 설득만이 아니라 감정적으로 이니시를 걸 수도 있어야 한다.
- **ADR은 미래를 위한 문서다.** Plan은 작업을 위한 도구이고, ADR은 "왜 그렇게 했는가"를 남기는 것. 같은 논의를 반복하지 않고, 결정을 뒤집을 때도 근거를 볼 수 있고, 새 팀원 온보딩 비용도 줄어든다.
- **AI에 끌려가지 않으려면**: 작은 단위로 요청하고, 결과를 검증하고, 테스트로 보호 범위를 만들고, diff를 설명할 수 있어야 한다.

## 2단계: 리팩터링 완성하기

### 무엇을 했는가

총 7단계로 나눠서 진행했다.

**작동 변경 (2개)**
1. `@Transactional` 적용 — 10개 Service 메서드에 트랜잭션 경계 설정
2. `Order.totalPrice` 영속화 — 주문 시 계산된 금액을 DB에 저장

**구조 변경 (5개)**
3. 가격 계산 로직을 `Order` 생성자로 이동 — 중복 계산 제거
4. 인증 중복 코드 제거 — `@LoginMember` + `HandlerMethodArgumentResolver`
5. Tell Don't Ask 원칙 적용 — 판단 로직을 엔티티로 이동
6. 메서드 이름 개선 — 역할에 맞는 이름으로 변경
7. Law of Demeter 위반 해소 — 엔티티 위임 메서드 추가

작동 변경마다 테스트로 증거를 남겼고, ADR 5개를 작성했다. 최종 107개 테스트 전부 통과.

## 아쉬운 점

### AI에게 주도권을 뺏겼다

가장 아쉬운 점이다. CLAUDE.md에 "한 단계씩, 승인받고 진행"이라고 적어뒀는데, 단계 5~7에서 Claude가 승인 없이 연속으로 코드를 수정해버렸다. 결과물 자체는 괜찮았지만, 내가 중간에 확인하고 커밋할 타이밍을 놓쳤다. 수업에서 "AI가 앞서 달리면 즉시 멈춘다"라고 했는데 지키지 못한 셈이다.

도구가 빠르게 해준다고 해서 내가 검토하는 과정을 생략하면 안 된다. AI한테 맡기더라도 내가 속도를 조절해야 한다는 걸 체감했다.

### step2_plan.md 덮어쓰기

plan 파일을 단계별로 누적해야 하는데, Claude가 매번 덮어써서 이전 단계의 plan이 사라지고 있었다. 중간에 발견하고 수정했지만, 처음부터 지시를 더 명확하게 줬어야 했다.

### Wish Demeter 위반 미해결

`Wish.getProductId()`를 추가하면 Spring Data JPA 파생 쿼리와 충돌하는 문제가 있었는데, `@Query`로 JPQL을 직접 쓰는 대안을 충분히 검토하지 않고 빠르게 미적용으로 결정했다.

## 배운 것

- **구조 변경과 작동 변경을 분리하면 diff가 명확해진다.** 처음엔 번거롭게 느껴졌는데, 실제로 커밋을 나눠보니 각각의 diff가 한 가지 목적만 담고 있어서 나중에 뭘 바꿨는지 금방 파악할 수 있었다.
- **작동 변경은 "붙였으니 되겠지"가 아니라 증거로 증명해야 한다.** 트랜잭션 롤백을 증명하려면 실패를 유도하고 상태를 재조회해야 한다. totalPrice도 1차 캐시를 날리고 DB에서 다시 읽어서 확인했다.
- **리뷰 피드백이 다음 단계의 방향이 된다.** 1단계에서 받은 "getter 대신 객체에 메시지를 전달하라"는 피드백이 2단계 Tell Don't Ask 적용으로 이어졌다. `@Transactional` 미적용에 대한 코멘트도 2단계 첫 작업이 됐다.
- **AI 도구는 지시를 명확하게 줘야 한다.** "한 번에 하나씩"이라고 적어놔도 AI는 맥락상 다음 것도 같이 해버린다. "하나 끝나면 반드시 멈추고 보고해라"처럼 구체적으로 제약을 걸어야 한다.
- **ADR을 쓰면 같은 고민을 반복하지 않는다.** Spring Data JPA 파생 쿼리 충돌 같은 건 ADR로 남겨뒀으니, 다음에 비슷한 상황이 오면 바로 참고할 수 있다.
