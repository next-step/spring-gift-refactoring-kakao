# 2단계 리팩토링 전략

## 현재 상태 분석 요약

| 구분 | 문제 | 파일 |
|------|------|------|
| 트랜잭션 | OrderService.createOrder에 @Transactional 없음 — 3개 저장 연산이 원자적이지 않음 | OrderService.java |
| 누락 작동 | 주문 후 위시리스트 정리 미구현 (wishRepository 주입만 되어있음) | OrderService.java |
| 누락 작동 | OrderController의 IllegalArgumentException이 500 반환 (핸들러 누락) | GlobalExceptionHandler.java |
| 도메인 누수 | AdminProductController가 Service 없이 Repository 직접 사용, 이름 검증 중복 | AdminProductController.java |
| 도메인 누수 | AdminMemberController가 Service 없이 Repository 직접 사용, 등록/충전 로직 중복 | AdminMemberController.java |
| 도메인 누수 | KakaoAuthController에 회원 자동가입 + 토큰 발급 로직이 컨트롤러에 존재 | KakaoAuthController.java |
| 중복 | 가격 계산(price × quantity)이 OrderService와 KakaoMessageClient에 중복 | OrderService.java, KakaoMessageClient.java |
| 중복 | 인증 체크(extractMember + null 체크 + 401 반환)가 OrderController 2회, WishController 3회 반복 | OrderController.java, WishController.java |
| 불일치 | AdminProductController는 NoSuchElementException, 나머지는 IllegalArgumentException 사용 | AdminProductController.java |

## 작업 순서

### Phase 1: 트랜잭션 경계 세우기

- [ ] 1-1. OrderService.createOrder에 @Transactional 적용
  - **바꾸는 것**: 3개 저장 연산을 원자적으로 묶음
  - **바꾸지 않는 것**: 정상 흐름의 결과
  - **증명**: 재고 차감 후 포인트 부족 시 재고가 롤백되는지 테스트로 검증

### Phase 2: 누락된 작동 구현

- [ ] 2-1. GlobalExceptionHandler를 전역 적용으로 변경 + 예외 타입 통일, 테스트 수정 (500→400)
  - **바꾸는 것**: OrderController 등에서 IllegalArgumentException 발생 시 500→400 반환. AdminProductController의 NoSuchElementException을 IllegalArgumentException으로 통일(또는 GlobalExceptionHandler에 NoSuchElementException 핸들러 추가)
  - **바꾸지 않는 것**: 기존 3개 컨트롤러의 400 동작
  - **증명**: 재고 부족/포인트 부족 테스트가 400을 기대하도록 수정
- [ ] 2-2. 주문 완료 후 위시리스트 정리 구현
  - **바꾸는 것**: 주문한 상품이 위시리스트에 있으면 삭제
  - **바꾸지 않는 것**: 위시리스트에 없는 상품 주문 시 기존 동작
  - **증명**: 위시 추가 → 주문 → 위시 목록 재조회하여 삭제 확인 테스트

### Phase 3: 도메인 책임 되찾기

구조 변경(서비스 추출)과 작동 변경을 분리하여 커밋한다.

- [ ] 3-1. AdminProductController → ProductService 위임 (구조 변경)
  - 이름 검증, 상품 생성/수정/삭제 로직을 ProductService로 이동
  - 중복 제거: 이름 검증 로직이 한 곳으로 통합
- [ ] 3-2. AdminMemberController → MemberService 위임 (구조 변경)
  - 회원 생성, 포인트 충전 로직을 MemberService로 이동
  - 중복 제거: 이메일 중복 체크가 한 곳으로 통합
- [ ] 3-3. KakaoAuthController → 서비스 계층으로 로직 이동 (구조 변경)
  - 카카오 OAuth 콜백 처리(자동가입, 토큰 업데이트, JWT 발급)를 서비스로 이동
- [ ] 3-4. 가격 계산 중복 제거 (구조 변경)
  - Order 또는 도메인에 totalPrice 계산 책임 부여
  - OrderService, KakaoMessageClient의 중복 계산 제거
- [ ] 3-5. 인증 체크 중복 제거 (구조 변경)
  - OrderController 2회, WishController 3회 반복되는 extractMember + null 체크 + 401 반환 패턴 제거
  - ArgumentResolver를 활용해 컨트롤러 메서드에 Member를 자동 주입하거나, 기존 AuthenticationResolver를 예외 기반으로 전환

### Phase 4: 검증 강화

- [x] 4-1. 트랜잭션 롤백 검증 테스트 추가 — `fail_insufficientPoints_shouldNotSubtractStock` 작성 완료 (Phase 1 적용 전이므로 의도적 실패 상태)
- [ ] 4-2. 기존 테스트 정리
  - 500→400 변경에 따른 테스트 수정 반영 확인

### Phase 5: 누락 기능 및 트랜잭션 개선

- [ ] 5-1. 옵션 수정 API 추가 (작동 변경 — 테스트 먼저)
  - **바꾸는 것**: PUT /api/products/{productId}/options/{optionId} 엔드포인트 추가
  - **바꾸지 않는 것**: 기존 GET/POST/DELETE 동작
  - **증명**: 수정 성공, 존재하지 않는 옵션/상품, 이름 검증 실패, 중복명 테스트
- [ ] 5-2. 카카오 알림을 트랜잭션 밖으로 분리 (구조 변경)
  - **바꾸는 것**: sendKakaoMessageIfPossible 호출 위치를 @Transactional 범위 밖으로 이동
  - **바꾸지 않는 것**: 알림 발송 자체의 best-effort 동작
  - **증명**: 기존 주문 테스트 통과 확인

## 향후 검토 사항 (이번 범위 밖)

작동 변경이 수반되므로 현재 목표(구조 변경, 작동 유지)와 분리하여 이후 단계에서 검토한다.

- Password null-safety — Kakao 로그인 회원은 password 없이 생성되나, 일반 로그인 시 null 체크만 존재 (MemberService, KakaoAuthController)
- Order/Wish의 memberId primitive FK — `@ManyToOne` 대신 `Long memberId`로 관리. cascade/fetch 불가 (의도적 설계 여부 확인 필요)
