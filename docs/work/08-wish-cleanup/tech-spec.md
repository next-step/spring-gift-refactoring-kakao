# 위시 정리 기술 명세

주문 흐름 주석의 6단계 "cleanup wish"를 구현한다. 주문한 회원의 위시에서 주문한 상품을 뺀다. 작동 변경이다.

- 작성일: 2026-11-27
- 기준 브랜치: `M32k`
- 용어는 [`docs/glossary.md`](../../glossary.md)를 따른다.
- 관련 확인 필요 목록: [`docs/open-questions.md`](../../open-questions.md) 8번(위시 정리 미구현), 9번(OrderController의 WishRepository)
- 관련 문서: [ADR 0001](../../adr/0001-order-transaction-boundary.md), [ADR 0002](../../adr/0002-order-notification-outbox.md), [`docs/work/02-acceptance-test/test-strategy.md`](../02-acceptance-test/test-strategy.md)

## 정해진 결정

- 주문한 회원의 위시에서 주문한 상품을 뺀다.
- 주문 커밋 뒤에 따로 한다. 위시 정리가 실패해도 주문은 성공(201)하고 위시는 남는다. 실패는 로그로 남긴다(빈 catch 금지).
- 응답 코드는 바꾸지 않는다.

## 1. 지금 작동

- `OrderService`의 흐름 주석에는 `// 6. cleanup wish`(`OrderService.java:45`)가 있다. 하지만 `createOrder`(`:49-71`)에는 위시를 건드리는 코드가 없다. 주문 저장(`:65-66`) 다음이 바로 주문 알림 저장(`:68-69`)이다.
- 그래서 주문한 상품이 위시에 그대로 남는다(open-questions 8번, curl로 확인함).
- `gift.order` 패키지는 `gift.wish`에 의존하지 않는다.

## 2. 바뀔 작동

| 경우 | 지금 | 바뀐 뒤 |
|---|---|---|
| 위시에 담은 상품의 옵션을 주문 | 위시가 그대로 남는다 | 주문이 커밋된 뒤 그 회원의 위시에서 그 상품이 빠진다 |
| 위시 정리 실패 | (해당 없음) | 주문은 201이고 위시는 남는다. warn 로그를 남긴다 |

위시를 찾는 기준은 "주문한 회원 + 주문한 옵션의 상품"이다.
- 주문 수량과 상관없이 그 상품의 위시를 뺀다.
- 같은 회원·상품 위시가 여러 개면 모두 뺀다.
  - API로는 중복이 생기지 않는다. 담을 때 이미 있으면 기존 위시를 돌려준다(`WishService.java:43-49`).
  - 하지만 DB에는 (member_id, product_id) unique 제약이 없다(`V1__Initialize_project_tables.sql:29-36`).
  - 그래서 하나만 지우거나 `Optional`로 하나만 찾는 방식(중복이 있으면 예외)은 쓰지 않는다.

## 4. 구조: 이벤트 비교

07처럼 주문 트랜잭션 안에서 이벤트를 발행한다. `@TransactionalEventListener(AFTER_COMMIT)` 리스너(`OrderWishCleanupListener`)가 받아, 별도 빈(`OrderWishCleanupExecutor`)의 `REQUIRES_NEW` 트랜잭션에서 위시를 지운다. 리스너에는 트랜잭션을 붙이지 않는다(07의 `OrderNotificationRelay`/`OrderNotificationDispatcher`와 같은 구조).
- 빈을 나누는 이유는 둘이다.
  - 커밋 때 나는 예외까지 리스너의 catch가 잡아 warn 로그를 남기게 하려는 것이다. 트랜잭션은 메서드가 끝난 뒤 프록시에서 커밋되므로, 리스너 메서드에 트랜잭션을 붙이면 커밋 때 예외가 그 catch 밖에서 난다.
  - 같은 빈 안의 호출은 프록시를 거치지 않아 `@Transactional`이 걸리지 않는다.
- 응답 코드 때문은 아니다. AFTER_COMMIT 리스너는 afterCompletion에서 불리고, 여기서 난 예외는 Spring이 error 로그만 남기고 삼킨다(spring-tx 6.2 `TransactionSynchronizationUtils.invokeAfterCompletion`). 그래서 리스너 밖으로 예외가 나가도 응답은 201 그대로다.

| | A. 07의 `OrderNotificationCreatedEvent`를 같이 쓴다 | B. 주문마다 새 이벤트(`OrderPlacedEvent(orderId, memberId, productId)`) |
|---|---|---|
| 발행 시점 | 카카오 액세스 토큰이 있는 회원에게만 발행된다(`OrderService.java:73-80`) | 성공한 주문마다 발행된다 |
| 토큰 없는 회원 | 위시가 정리되지 않는다. 초기 데이터 회원은 모두 토큰이 없어서 대부분의 주문이 빠진다 | 정리된다 |
| 담긴 값 | 알림 번호뿐이다. 상품을 알려면 알림 → 주문 → 옵션 → 상품을 다시 읽어야 한다 | 정리에 필요한 값을 바로 담는다 |
| 의미 | "알림이 만들어졌다"에 위시 정리를 엮는다. 알림 규칙이 바뀌면 위시 정리도 따라 바뀐다 | "주문이 됐다"는 사실에 각자 반응한다 |

**결정: B.** 토큰 없는 회원의 위시도 정리해야 해서다.

- 주문 알림은 지금처럼 자기 이벤트를 쓴다. 알림까지 B로 옮기는 것은 이번 범위가 아니다.
- 리스너 두 개(위시 정리, 주문 알림)가 같은 커밋 뒤에 돈다.
  - 서로 결과에 기대지 않으므로 순서(`@Order`)는 정하지 않는다.
  - 한쪽이 실패해도 다른 쪽은 돈다. 각자 예외를 잡고 로그를 남긴다.
- 위치: 리스너와 정리 코드는 `gift.wish`에 둔다. `gift.wish`가 `gift.order`의 이벤트에 의존하고, `gift.order`는 `gift.wish`를 모른다(의존 방향이 한쪽이다).

## 5. 위시 정리 실패를 테스트에서 만드는 방법

`src/main`에 테스트만을 위한 스위치를 넣는 방법은 뺐다.

| | 가. 정리 작업을 인터페이스 뒤에 두고, 테스트에서 감싸개를 `@Primary`로 | 나. `WishRepository`를 `@MockitoSpyBean`으로 감싸 삭제 메서드만 예외 | 다. H2 트리거로 `wish` 삭제를 DB에서 막기 |
|---|---|---|---|
| src/main 변경 | 인터페이스(`WishCleaner`)와 구현(예: `RepositoryWishCleaner`) | 없음 | 없음 |
| 테스트 | 감싸개가 평소에는 진짜 구현에 맡기고, 정해 두면 예외를 던진다. 07의 `FakeOrderNotificationSender`와 같은 방식이다 | 스파이 설정과 시나리오마다 되돌리기가 필요하다. Spring Data 저장소 프록시를 감싸는 것이라 깨지기 쉽다 | 테스트용 Java 트리거 클래스를 만들고 시나리오에서 `CREATE TRIGGER`를 실행한다. Flyway clean이 트리거를 지워서 되돌리기는 자동이다 |
| 실패하는 곳 | 정리 작업의 경계 | 저장소 호출 | DB(가장 실제에 가깝다) |
| 비용 | 인터페이스 하나가 늘어난다 | Mockito를 Cucumber 컨텍스트에 들인다. 모든 시나리오의 빈이 바뀐다 | H2 전용이라 DB를 바꾸면 다시 만들어야 한다 |

**결정: 가.** 07 가짜 발송기와 같은 방식이다. 스파이는 저장소 프록시를 감싸서 깨지기 쉽고, 트리거는 H2에 묶인다.

## 6. 구조 변경과 작동 변경의 순서

구조 변경(`refactor:`)을 먼저 끝낸다. 구조 변경에서는 인수 테스트를 고치지 않는다.

| 순서 | 종류 | 내용 |
|---|---|---|
| R1 | refactor | `gift.wish`에 `WishCleaner` 인터페이스와 구현을 둔다. 구현은 `WishRepository`에 "회원 + 상품으로 모두 지우기" 메서드를 더해 쓴다. 아직 부르는 곳은 없다 |
| R2 | refactor | `createOrder`가 주문 저장 뒤 `OrderPlacedEvent`를 발행한다. 아직 받는 리스너가 없어서 작동은 같다 |
| T1 | test | 테스트 감싸개(`@Primary`)와 단계 정의("위시 정리가 실패한다"). 시나리오는 아직 더하지 않는다 |
| B1 | feat | 테스트 먼저(7장 W-1~W-5) → 실패 출력 → `gift.wish`의 AFTER_COMMIT 리스너, `REQUIRES_NEW` 정리, 실패 warn 로그. ADR 0003을 같은 커밋에 넣는다 |
| D | docs | 11장 |

## 7. 인수 테스트 계획

위시는 위시 목록 API(`GET /api/wishes`)로 다시 조회한다. 기존 단계 `(user1|user2)의 위시 번호는 …다`(`WishSteps.java:25`)를 쓴다.

새 파일 `wish-cleanup.feature`에 둔다. 스토리 16(주문)의 일부라 16-15~16-19로 번호를 붙인다.

초기 위시(`V2__Insert_default_data.sql:28-35`):
- user1(회원 2): 위시 1 = 상품 1, 위시 2 = 상품 3
- user2(회원 3): 위시 3 = 상품 2, 위시 4 = 상품 5

| | 시나리오 | 초기 데이터에서 고른 것 | 확인 |
|---|---|---|---|
| W-1 | user1이 위시에 담은 상품을 주문하면 그 위시가 빠진다 | 옵션 5(상품 3 나이키 에어맥스, 179,000원, 재고 15) | 201 → user1 위시 번호 1 |
| W-2 | 위시에 없는 상품을 주문하면 위시는 그대로다 | 옵션 7(상품 5 제주 감귤 5kg, 25,000원). user1 위시에 상품 5는 없다 | 201 → user1 위시 번호 그대로 1, 2 |
| W-3 | 다른 회원의 같은 상품 위시는 남는다 | user1이 상품 5를 위시에 담는다(201, 응답 번호로 확인). 그다음 옵션 7을 주문한다. user2 위시 4가 상품 5다 | 201 → user1 위시 번호 1, 2 / user2 위시 번호 그대로 3, 4 |
| W-4 | 실패한 주문(포인트 부족 500)에서는 위시가 그대로다 | user2(포인트 3,000,000)가 옵션 3(상품 2 아이폰 16, 1,350,000원)을 주문 수량 3(4,050,000원)으로 주문한다. user2 위시 3이 상품 2다 | 500 → user2 위시 번호 그대로 3, 4 |
| W-5 | 위시 정리가 실패해도 주문은 201이고 위시는 남는다 | W-1과 같은 주문 + "위시 정리가 실패한다" | 201, user1 주문 내역 2 → 3건, user1 위시 번호 그대로 1, 2 |

W-3에서 새로 담은 위시는 번호를 미리 정하지 않는다. 남은 번호가 1, 2뿐인지로 빠졌는지를 본다.

## 8. 고칠 테스트와 먼저 실패할 곳

R1, R2, T1을 마친 상태에서 코드를 바꾸기 전에 돌렸을 때:

| 시나리오 | 바꾸기 전 | 실패하는 단계 |
|---|---|---|
| W-1 | 실패 | "user1의 위시 번호는 1이다"(실제 1, 2) |
| W-3 | 실패 | "user1의 위시 번호는 1, 2다"(실제 1, 2, 새 번호) |
| W-2, W-4 | 통과 | 지키는 시나리오다 |
| W-5 | 통과 | 지금은 정리를 하지 않아서 처음부터 통과한다. 코드를 바꾼 뒤 "실패 설정을 빼면 위시 단계에서 실패하는지"를 일부러 틀려서 확인한다 |

## 9. ArchUnit

- 새 클래스 이름은 `…Service`로 끝나지 않게 한다. 예: `OrderPlacedEvent`, `WishCleaner`, `RepositoryWishCleaner`, `OrderWishCleanupListener`.
- `WishRepository`를 쓰는 곳은 지금 `WishService` 하나다(`WishService.java:10`). 이번에 정리 구현(`gift.wish`)이 더해진다. 컨트롤러는 쓰지 않으니 규칙 A에 걸리지 않는다.
- `OrderService`는 이벤트를 발행할 뿐이고 `gift.wish`나 `WishRepository`에 의존하지 않는다.
- 규칙(`LayerArchitectureTest`)은 고치지 않는다.

## 10. 남길 ADR

- `0003. 위시 정리는 주문 커밋 뒤 따로 하고, 실패해도 주문은 성공한다` (본문은 아직 쓰지 않는다. B1과 같은 커밋에 넣는다)
- "결과"에 넣을 생기는 문제:
  - 위시 정리가 실패하면 주문한 상품이 위시에 남는다. 재시도는 없다.
  - 주문 응답이 위시 정리를 기다린다. 커밋 뒤 같은 스레드에서 하기 때문이다. 같은 커밋 뒤의 주문 알림(ADR 0002)과 함께 기다린다.
  - 주문 커밋과 위시 정리 사이에 앱이 꺼지면 위시가 남는다. 아웃박스처럼 기록하지 않는다.
  - 위시 정리와 주문 알림은 순서를 정하지 않는다.
