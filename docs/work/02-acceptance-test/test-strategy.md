# 인수 테스트 전략

사용자 스토리의 인수 조건을 자동 인수 테스트로 어떻게 옮겼는지 정리한 문서다. 이번 대상은 1-1~1-3, 2-1~2-3, 4-1~4-4, 5-1, 6-1~6-2, 7-1~7-3, 8-1~8-6, 9-1~9-4, 10-1~10-9, 11-1~11-6, 12-1~12-7, 13-1~13-3, 14-1~14-3, 15-1~15-3, 16-1~16-7, 17-1~17-4다(스토리 16개, 시나리오 68개).
인수 조건 본문은 `src/test/resources/features/`의 feature 파일에만 있고, [`docs/user-stories.md`](../../user-stories.md)에는 feature 파일 위치와 시나리오 번호만 적는다.

- 작성일: 2026-11-22
- 기준 브랜치: `M32k`
- 용어는 [`docs/glossary.md`](../../glossary.md)를 따른다.

---

## 1. 목표

- 인수 테스트는 지금 동작을 그대로 고정한다.
- 버그처럼 보이는 동작도 지금 동작이면 그대로 검증한다. 예: 16-2는 포인트가 부족하면 500이 오고, 재고는 줄어든 채로 남는다(open-questions 3번).
- 프로덕션 코드(`src/main`)는 고치지 않는다.

## 2. 고른 기준

미션 조건은 스토리 3개 이상, 시나리오 5개 이상, 주문 흐름 포함, 확인 필요 목록에서 "지금 그대로 지킬 작동" 1개 이상이다.

**공통 기준**
- 1단계에서 요청으로 직접 확인한 결과가 있는 작동만 골랐다. 기대값을 짐작이 아니라 확인한 결과로 쓸 수 있다.
- 카카오처럼 외부 서비스에 기대는 작동은 뺐다. 테스트 결과가 외부 상태에 흔들리지 않게 하려고.
- 성공만이 아니라, 실패한 뒤 상태가 어떻게 남는지를 확인하는 시나리오를 넣었다.

| 스토리 | 시나리오 | 고른 이유 |
|---|---|---|
| 16. 주문 | 16-1 정상 주문 | 서비스의 핵심 흐름. 재고, 포인트, 주문 내역 세 곳이 함께 바뀐다 |
| 16. 주문 | 16-2 포인트 부족 | 실패했는데 재고가 줄어든 채 남는다(open-questions 3번). 버그처럼 보이지만 지금 작동으로 고정할 대상이다. 리팩터링 중 가장 바뀌기 쉬운 작동이다. 4단계에서 ADR 0001로 바뀜(재고도 그대로) |
| 16. 주문 | 16-3 재고 부족 | 같은 500이어도 실패 단계에 따라 상태가 남지 않는다(open-questions 12번). 16-2와 짝을 이뤄 차이를 고정한다 |
| 15. 위시 삭제 | 15-1 남의 위시 삭제 | 다른 회원의 데이터를 지키는 작동이다. 403(404가 아님)을 고른 지금 작동을 고정한다(open-questions 5번) |
| 7. 상품 등록 | 7-1 등록 후 조회 | 201만이 아니라 다시 조회해서 저장된 값을 확인한다 |
| 7. 상품 등록 | 7-2, 7-3 15자/16자 | 상품명 규칙의 경계값이다. 실패한 뒤 상품 수가 그대로인지도 본다 |

**3단계 안전망으로 더한 것**

서비스로 옮기기 전에 안전망으로 더한 시나리오다. 항목 이름(L1~L6, O1~C1)은 [`docs/work/05-service-layer/tasks.md`](../05-service-layer/tasks.md)를 따른다.

| 스토리 | 시나리오 | 더한 이유 |
|---|---|---|
| 16. 주문 | 16-4~16-7 | O1~O4 안전망(L1). 없는 옵션 404, 로그인 토큰 401·400, 주문 수량 0 |
| 17. 주문 내역 | 17-1~17-4 | 주문 내역 조회 |
| 1·2. 회원 가입·로그인 | 1-1~1-3, 2-1~2-3 | M1 안전망(L2) |
| 13~15. 위시 | 13-1~13-3, 14-1~14-3, 15-2~15-3 | W1 안전망(L3). 200과 201, 404와 403의 차이 |
| 4·8·9. 상품 | 4-1~4-4, 8-1~8-6, 9-1~9-4 | P1 안전망(L4). 쪽 나눔, 확인 순서, 외래 키 500 |
| 6·11·12. 옵션 | 6-1~6-2, 11-1~11-6, 12-1~12-7 | Op1 안전망(L5). 확인 순서, 외래 키 500 |
| 5·10. 카테고리 | 5-1, 10-1~10-9 | C1 안전망(L6). `@Valid`가 먼저, 외래 키·unique 500 |

**이번에 넣지 않은 것**
- 주문 알림: 카카오 서버에 기대서 HTTP 인수 테스트로 확인하기 어렵다.
- 카카오 로그인(스토리 3): 카카오 서버에 기대서 HTTP 인수 테스트로 확인하기 어렵다. K1은 코드 검토와 직접 로그인으로 확인했다.
- 관리자 화면(스토리 18~26): HTML과 302를 검사해야 해서 안전망을 만들기 어렵다. [`docs/work/05-service-layer/tasks.md`](../05-service-layer/tasks.md)의 "옮기지 않은 것" 참고.

## 3. 도구

| 도구 | 쓰는 곳 |
|---|---|
| Cucumber (cucumber-bom 7.20.1) | 시나리오를 `src/test/resources/features/*.feature`에 Given/When/Then으로 쓴다. 인수 조건 본문은 feature 파일에만 쓰고, 수의 근거(주문 금액 계산 등)는 시나리오 위에 Gherkin 주석으로 남긴다 |
| RestAssured (버전은 Spring Boot가 관리) | HTTP 요청을 보내고 응답을 검증한다 |
| `@SpringBootTest(webEnvironment = RANDOM_PORT)` | 실제 서버를 임의 포트로 띄운다. `@LocalServerPort`로 받은 포트로 요청한다 |

테스트 코드는 `src/test/java/gift/acceptance`에 있다.

## 4. 테스트 데이터: 매 시나리오 전에 초기 데이터로 되돌린다

시나리오가 번호를 직접 쓴다(옵션 1, 위시 3, 상품 6개에서 7개). 그래서 데이터뿐 아니라 자동 증가 번호까지 처음으로 되돌려야 한다.

**방법**: 매 시나리오 전에 Flyway `clean()` 다음 `migrate()`를 실행한다(`DatabaseHook`).
- 테스트 설정(`src/test/resources/application-test.properties`)에서 `spring.flyway.clean-disabled=false`로 허용한다.
- 앱과 같은 V1(테이블)과 V2(초기 데이터)를 다시 실행한다. 그래서 초기 데이터와 번호가 실제 앱을 처음 켰을 때와 같다.
- 테이블 목록을 테스트 코드에서 따로 관리하지 않는다. 마이그레이션이 늘어도 그대로 따라간다.

**쓰지 않은 방법**

| 방법 | 쓰지 않은 이유 |
|---|---|
| TRUNCATE + 번호 초기화 + V2 다시 실행 | 더 빠르지만, H2 전용 SQL과 테이블 목록을 테스트 코드가 직접 관리해야 한다 |
| 매 시나리오 `@DirtiesContext` | 시나리오마다 서버를 다시 띄워서 매우 느리다 |
| `@Transactional` 롤백 | RANDOM_PORT에서는 요청이 테스트와 다른 스레드에서 처리돼 롤백되지 않는다 |

**실행 순서와 상관없는지 확인하는 방법**
- 16-1과 16-2는 같은 옵션 1(재고 10)을 쓰고, 둘 다 재고 10에서 시작한다고 확인한다.
- 7-1과 7-2는 둘 다 상품 수 6에서 시작한다고 확인한다.
- 이 두 쌍이 한 번의 실행에서 모두 통과하면 초기화가 동작한다는 뜻이다.

## 5. 검증 방법: 포인트와 주문 알림 상태는 DB, 나머지는 API

| 값 | 확인 방법 |
|---|---|
| 상품, 상품 수 | `GET /api/products/{id}`, `GET /api/products`의 `totalElements` |
| 재고 | `GET /api/products/{productId}/options` |
| 위시 | `GET /api/wishes` (회원의 로그인 토큰) |
| 주문 내역 | `GET /api/orders`의 `totalElements` (회원의 로그인 토큰) |
| **포인트** | **DB**: `select point from member where email = ?` |
| **주문 알림 상태** | **DB**: `select status, attempt_count, last_error, sent_at from order_notification where order_id = ?` (07에서 더함, ADR 0002) |

**포인트와 주문 알림 상태를 DB에서 확인하는 이유**
- 회원이 자기 포인트를 조회하는 API가 없다(open-questions 4번).
- 주문 알림의 상태(보낼 것, 보냄, 실패)와 시도 횟수를 보는 API도 없다(ADR 0002).
- 미션 규칙상 API로 확인할 수 없는 값은 DB에서 확인해도 된다.

**관리자 화면으로 포인트를 확인하지 않는 이유**
- 관리자 화면(`/admin/members`)에서도 포인트를 볼 수 있다.
- 하지만 관리자 화면에 인증이 없는 것은 확인 필요 목록 13번, 22번에 올라 있다.
- 나중에 관리자 화면에 인증이 붙으면, 포인트를 보려고 관리자 화면을 쓰는 주문 테스트까지 깨질 수 있다.

**비용**
- 포인트 확인은 테이블과 컬럼 이름(`member.point`)에 묶인다.
- 주문 알림 확인은 `order_notification` 테이블과 열 이름에 묶인다.
- DB를 읽는 곳은 `MemberSteps`의 포인트 확인 단계와 `OrderNotificationSteps`의 주문 알림 단계다. 저장 방식이 바뀌거나 조회 API가 생기면 그 단계만 고치면 된다.

## 6. 주문 알림: 외부 호출이 없다 (코드로만 판단)

- 주문 알림은 회원에게 카카오 액세스 토큰이 있을 때만 만든다(`OrderService.java:73-81`). 없으면 카카오로 요청을 보내지 않는다.
- 07부터 16-8~16-14는 토큰을 DB로 넣어 알림 경로를 지난다. 이때 알림은 가짜 발송기(`FakeOrderNotificationSender`)가 받아서 카카오로 나가지 않는다.
- 초기 데이터의 회원은 카카오 액세스 토큰이 비어 있다. V2의 회원 insert에 이 값이 없다.
- 카카오 액세스 토큰은 카카오 로그인 콜백(`KakaoAuthController.java:54`에서 부르는 `MemberService.java:39-40`)에서만 저장된다. 테스트는 이메일 로그인(`POST /api/members/login`)만 쓴다.
- 따라서 이번 시나리오에서는 카카오로 나가는 호출이 없다.

## 7. 주요 의사 결정

| 결정 | 고른 것 | 이유 |
|---|---|---|
| 버그처럼 보이는 작동 | 고치지 않고 지금 작동으로 고정 (16-2) | 고칠지는 사람이 정한다. 그때까지는 작동이 바뀌면 테스트가 알려야 한다. 16-2는 4단계에서 ADR 0001로 바뀜(재고도 그대로) |
| 16-2의 회원 | 처음부터 포인트가 부족한 user2로 한 번 주문 | 1단계에서는 user1이 두 번 주문했다. 한 시나리오에 행동 하나만 담으려고 바꿨고, 앱을 다시 켜고 직접 요청해 같은 결과(500, 재고가 10에서 9로 줄어듦)를 확인했다 |
| 테스트 데이터 | Flyway clean + migrate | 4장 참고 |
| 포인트 확인 | DB (포인트만) | 5장 참고. Claude Code는 관리자 화면 HTML을 추천했지만, 관리자 화면 인증 문제(13, 22번) 때문에 고르지 않았다 |
| 새로 만든 데이터의 번호 | 응답에 나온 번호로 다음 요청 | 번호를 미리 정하면 실행 순서나 초기 데이터가 바뀔 때 깨진다 |
| 인수 조건의 위치 | feature 파일에만 | 두 곳에 쓰면 한쪽만 고쳐져 어긋난다. user-stories에만 있던 설명은 Gherkin 주석으로 옮겼다 |
| 테스트를 믿는 근거 | 기대값을 일부러 틀리게 바꿔 실패를 확인 | 16-2의 재고 기대값을 9에서 10으로 바꾸면 16-2만 실패했다. 통과만으로는 테스트가 무엇을 확인하는지 알 수 없다 |

## 8. 실행

```
./gradlew test --tests 'gift.acceptance.CucumberTest'
./gradlew test --tests 'gift.architecture.LayerArchitectureTest'
```

- 환경 변수는 필요 없다. `JWT_SECRET`은 예시 기본값이 있다(open-questions 23번).
- 결과 보고서는 `build/reports/tests/test/index.html`에 생긴다.
- 결과가 너무 빨리 나오면(예: 3초대가 1초 안쪽으로) Gradle이 이전 결과를 다시 쓴 것일 수 있다. `--rerun-tasks`를 붙여 다시 실행한다.
