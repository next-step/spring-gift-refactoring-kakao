# 주문 흐름 분석 (주문하기)

회원이 옵션을 골라 포인트로 주문할 때(`POST /api/orders`) 서비스 안에서 무슨 일이 어떤 순서로 일어나는지 정리한 문서다.

- 작성일: 2026-11-22
- 기준 브랜치: `M32k`
- 용어는 [`docs/glossary.md`](../../glossary.md)를 따른다.
- 표시 규칙
  - **(확인함)**: 사용자가 직접 요청을 보내 확인한 결과
  - **(코드로만 판단)**: 요청으로는 확인하지 않고 코드를 읽어 판단한 결과
- 읽은 범위: 주문 처리, 주문 기록, 로그인 토큰 확인, 회원의 포인트, 옵션의 재고, 상품의 가격, 주문 알림 발송. 그 밖은 맨 아래 "범위 밖"에 모았다.

---

## 1. 흐름 요약

회원이 로그인 토큰, 옵션, 주문 수량, 주문 메시지를 보내면 아래 순서로 처리하고 201과 주문 정보를 돌려준다.

| 단계 | 하는 일 | 저장 |
|---|---|---|
| 0. 요청 형식 확인 | 요청의 형식을 본다 | 없음 |
| 1. 로그인 확인 | 로그인 토큰으로 회원을 찾는다 | 없음 |
| 2. 옵션 확인 | 옵션으로 상품을, 상품으로 가격을 찾는다 | 없음 |
| 3. 재고 차감 | 옵션의 재고를 줄인다 | 바로 저장 |
| 4. 포인트 차감 | 회원의 포인트를 줄인다. 주문 금액 = 가격 × 주문 수량 | 바로 저장 |
| 5. 주문 저장 | 옵션, 회원, 주문 수량, 주문 메시지, 주문 시각을 주문으로 저장한다 | 바로 저장 |
| 6. 위시 정리 | 구현 없음 | 없음 |
| 7. 주문 알림 | 카카오 액세스 토큰이 있으면 본인 카카오톡으로 보낸다 | 없음 |

**관계 정리**
- 주문은 **옵션**을 가리킨다. 상품은 옵션을 거쳐서만 알 수 있다.
- 주문은 **회원**을 가리킨다. 받는 사람 정보는 없다.
- **재고**는 옵션에, **포인트**는 회원에, **가격**은 상품에 있다. 그래서 주문 한 번에 서로 다른 세 곳의 값을 읽거나 바꾼다.
- 재고 차감, 포인트 차감, 주문 저장은 **각각 따로 저장된다.** 하나로 묶여 있지 않아서, 중간 단계가 실패해도 앞에서 저장한 변경은 되돌아가지 않는다.

## 2. 단계별 표

| 단계 | 확인하는 것 | 저장하는 것 | 실패하면 응답 | 실패한 뒤 남는 상태 |
|---|---|---|---|---|
| 0. 요청 형식 확인 (주석에 없음) | 로그인 토큰을 담는 헤더가 있는지, 옵션을 골랐는지, 주문 수량이 1 이상인지 | 없음 | 400 (확인함: 헤더 없음, 주문 수량 0. 옵션을 고르지 않은 경우는 코드로만 판단) | 바뀐 것 없음 (코드로만 판단) |
| 1. 로그인 확인 | 로그인 토큰이 이 서비스가 만든 것이고 기한이 지나지 않았는지, 그 토큰의 회원이 지금도 있는지 | 없음 | 401 (확인함: 틀린 로그인 토큰. 기한이 지난 경우와 삭제된 회원은 코드로만 판단) | 바뀐 것 없음 (코드로만 판단) |
| 2. 옵션 확인 | 고른 옵션이 있는지 | 없음 | 404 (확인함) | 바뀐 것 없음 (코드로만 판단) |
| 3. 재고 차감 | 재고가 주문 수량 이상인지 | 줄어든 재고 (바로 저장) | 500 (확인함) | 재고와 포인트 모두 그대로 (확인함) |
| 4. 포인트 차감 | 주문 금액(상품 가격 × 주문 수량)이 1 이상인지, 포인트가 주문 금액 이상인지 | 줄어든 포인트 (바로 저장) | 500 (확인함, 포인트 부족) | **재고는 줄어든 채로 남는다.** 포인트는 그대로이고 주문 내역에도 없다 (확인함) |
| 5. 주문 저장 | 없음 | 주문 (옵션, 회원, 주문 수량, 주문 메시지, 주문 시각) | 500 (코드로만 판단, 저장 자체가 실패하는 경우) | 재고와 포인트는 줄어든 채 주문만 없다 (코드로만 판단) |
| 6. 위시 정리 | 구현 없음 (확인함: 맥북을 주문한 user1의 위시에 맥북이 그대로 남아 있음) | 없음 | 해당 없음 | 해당 없음 |
| 7. 주문 알림 | 회원에게 카카오 액세스 토큰이 있는지 | 없음 | 실패해도 응답에 영향 없음. 그대로 201 (코드로만 판단) | 주문은 그대로 성공한다. 실패했다는 기록은 남지 않는다 (코드로만 판단) |
| 응답 | 없음 | 없음 | 해당 없음 | 201과 주문 정보(주문 번호, 옵션, 주문 수량, 주문 시각, 주문 메시지) |

### 단계별 보충

**0. 요청 형식 확인**
- 이 확인은 주문 코드가 실행되기 전에 먼저 일어난다. 그래서 로그인 토큰도 없고 주문 수량도 0인 요청은 401이 아니라 400을 받는다. (코드로만 판단)
- 로그인 토큰을 담는 헤더가 아예 없는 경우도 여기서 400이 된다. (확인함)
- 주문 수량이 0이어도 400이 된다. (확인함)

**1. 로그인 확인**
- 헤더는 있지만 로그인 토큰이 틀리면 401이 된다. (확인함)
- 기한이 지났거나 그 회원이 삭제된 경우에도 같은 401이 된다. 어느 이유인지는 응답으로 구분되지 않는다. (코드로만 판단)
- 로그인 토큰에는 회원의 이메일이 들어 있고, 서비스는 그 이메일로 회원을 찾는다.

**3. 재고 차감**
- 재고가 모자라면 재고를 줄이기 **전에** 멈춘다. 그래서 아무것도 바뀌지 않는다. (확인함: 재고 50인 옵션에 51개 주문하면 500, 재고와 포인트 그대로)
- 재고가 충분하면 줄어든 재고를 **바로 저장**한다. 다음 단계가 실패해도 되돌리지 않는다.

**4. 포인트 차감**
- 주문 금액은 옵션이 아니라 **상품의 가격**으로 계산한다. 같은 상품의 옵션은 모두 같은 주문 금액이 된다.
- 포인트가 모자라면 500이 오지만, 3단계에서 저장한 재고 차감은 그대로 남는다. (확인함: 포인트 1,640,000인 회원이 3,360,000원 주문하면 500, 재고는 9에서 8로 줄고 포인트는 그대로, 주문 내역에 없음)
- 주문 금액이 1 미만이 되는 경우에도 같은 방식으로 500이 나고 재고만 줄어든다. 가격이 0인 상품이나, 가격 × 주문 수량이 너무 커서 숫자 범위를 넘는 경우가 여기에 해당한다. (코드로만 판단)

**7. 주문 알림**
- 카카오 로그인을 한 회원만 카카오 액세스 토큰이 있으므로, 이메일로만 회원 가입한 회원에게는 주문 알림을 보내지 않는다. (코드로만 판단)
- 주문 알림의 문구는 "🎁 선물이 도착했어요!"이고, 상품명, 옵션명, 주문 수량, 주문 금액, 주문 메시지가 담긴다. 받는 사람은 **주문한 본인**이다. (확인함: 카카오 로그인 회원으로 주문하면 본인 카카오톡에 "선물이 도착했어요")
- 보내다가 실패해도 그냥 넘어가고, 다시 보내지 않는다. (코드로만 판단)

## 3. 확인한 결과 모음

| 경우 | 응답 | 재고 | 포인트 | 주문 내역 | 근거 |
|---|---|---|---|---|---|
| 정상 주문 (맥북 옵션 1개, 포인트 5,000,000) | 201 | 10에서 9 | 5,000,000에서 1,640,000 | 생김 | 확인함 |
| 이어서 같은 주문 (포인트 부족) | 500 | 9에서 8 (줄어듦) | 그대로 | 없음 | 확인함 |
| 재고 부족 (재고 50에 51개) | 500 | 그대로 | 그대로 | 없음 | 확인함 |
| 주문 알림 (카카오 로그인 회원) | 201 | 해당 없음 | 해당 없음 | 해당 없음 | 확인함. 본인 카카오톡에 "선물이 도착했어요" |
| 로그인 토큰 헤더 없음 | 400 | 그대로 | 그대로 | 없음 | 응답은 확인함. 재고, 포인트, 주문 내역은 코드로만 판단 |
| 틀린 로그인 토큰 | 401 | 그대로 | 그대로 | 없음 | 응답은 확인함. 재고, 포인트, 주문 내역은 코드로만 판단 |
| 없는 옵션 | 404 | 그대로 | 그대로 | 없음 | 응답은 확인함. 재고, 포인트, 주문 내역은 코드로만 판단 |
| 주문 수량 0 | 400 | 그대로 | 그대로 | 없음 | 응답은 확인함. 재고, 포인트, 주문 내역은 코드로만 판단 |
| 주문한 상품의 위시 (맥북을 주문한 user1) | 해당 없음 | 해당 없음 | 해당 없음 | 해당 없음 | 확인함. 위시에 맥북이 그대로 남아 있음 |

## 4. 주석의 7단계와 실제 코드가 다른 곳

주문 코드에는 다음 7단계가 주석으로 적혀 있다: 1 로그인 확인, 2 옵션 확인, 3 재고 차감, 4 포인트 차감, 5 주문 저장, 6 위시 정리, 7 주문 알림.

| 주석 단계 | 실제 코드 | 차이 |
|---|---|---|
| (없음) | 요청 형식 확인이 1단계보다 먼저 일어난다 | 주석에 없는 단계가 맨 앞에 있다. 그래서 형식이 틀리면 로그인 여부와 상관없이 400이 된다. (코드로만 판단) |
| 2. 옵션 확인 | 옵션이 **있는지만** 확인한다 | 재고가 충분한지는 여기서 보지 않고 3단계 안에서 확인한다. |
| 3~5. 재고 차감, 포인트 차감, 주문 저장 | 세 단계가 각각 따로 저장된다 | 주석은 순서만 적었다. 실제로는 중간에 실패해도 앞 단계를 되돌리지 않는다. 포인트가 부족하면 재고만 줄어든 채로 남는다. (확인함) |
| 4. 포인트 차감 | 주문 금액을 계산하는 일이 이 단계 안에 들어 있다 | 주문 금액은 상품 가격으로 계산한다는 점이 주석에 드러나지 않는다. |
| 6. 위시 정리 | **구현되어 있지 않다** | 위시를 다룰 준비(위시 저장소 연결)만 되어 있고 쓰이지 않는다. 주문한 상품이 위시에 그대로 남는다. (확인함: 맥북을 주문한 user1의 위시에 맥북이 그대로 남아 있음) |
| 7. 주문 알림 | 카카오 액세스 토큰이 있는 회원에게만, 주문한 본인에게 보낸다. 실패는 무시한다 | 주석은 "알림을 보낸다"고만 적었다. 실제로는 보내지 않는 경우가 있고, 받는 사람이 선물을 받을 사람이 아니라 본인이다. 코드 안에는 "가능하면 보낸다(best-effort)"는 짧은 주석이 따로 있다. |

## 5. 범위 밖

주문 흐름을 읽다가 만났지만 이번에는 더 들어가지 않은 것들이다.

- **주문 내역 조회**(`GET /api/orders`)의 동작: 확인한 결과로 "실패한 주문은 내역에 없다"는 것만 적었다.
- **같은 옵션을 동시에 주문하는 경우**: 동시에 들어온 주문이 재고를 어떻게 나눠 쓰는지는 보지 않았다.
- **로그인 토큰을 만드는 방법과 유효 기간 설정**: 로그인 확인 단계에서 "기한이 지났는지 본다"는 것까지만 다뤘다.
- **카카오 쪽 메시지 API의 동작과 오류 종류**: 이 서비스가 실패를 무시한다는 것까지만 다뤘다.
- **상품 가격이 0인 상품이 실제로 등록될 수 있는지**: 4단계 보충의 "가격이 0인 상품"은 코드로만 판단한 가정이다. 관리자 화면과 API에서 가격을 어떻게 검사하는지는 확인하지 않았다.
- **오류 응답 본문의 형식**: 상태 코드만 다뤘다.
