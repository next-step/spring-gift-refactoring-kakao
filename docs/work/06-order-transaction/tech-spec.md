# 주문 트랜잭션 기술 명세

주문하기의 재고 차감, 포인트 차감, 주문 저장을 한 트랜잭션으로 묶는 작업이다. 작동 변경이다.

- 작성일: 2026-11-27
- 기준 브랜치: `M32k`
- 용어는 [`docs/glossary.md`](../../glossary.md)를 따른다.
- 관련 확인 필요 목록: [`docs/open-questions.md`](../../open-questions.md) 3번, 12번
- 관련 문서: [`docs/work/02-acceptance-test/test-strategy.md`](../02-acceptance-test/test-strategy.md) (포인트는 DB로 확인하는 이유)

## 목표

- 주문하기(`POST /api/orders`)의 재고 차감, 포인트 차감, 주문 저장을 한 트랜잭션으로 묶는다. 중간에 실패하면 앞의 변경도 되돌린다.
- 응답 코드는 바꾸지 않는다. 포인트 부족도 재고 부족도 지금처럼 500이다.
- 주문 알림은 이번에 아웃박스로 바꾸지 않는다. 다음 작업(07)에서 바꾼다.

## 1. 지금 작동

`OrderService.createOrder`(`OrderService.java:42-64`)에도 `OrderController`에도 `@Transactional`이 없다. 저장할 때마다 따로 커밋된다.

| 순서 | 코드 | 실패하면 |
|---|---|---|
| 1. 옵션 확인 | `optionRepository.findById(..).orElse(null)` (`:44-47`) | 404. 아무것도 바뀌지 않는다 |
| 2. 재고 차감 | `option.subtractStock(..)` → `optionRepository.save(option)` (`:50-51`) | 재고 부족이면 저장 전에 예외 → 500. 아무것도 바뀌지 않는다(12번) |
| 3. 포인트 차감 | `member.deductPoint(totalPrice)` → `memberRepository.save(member)` (`:54-56`) | 포인트 부족이면 예외 → 500. **2에서 저장한 재고는 줄어든 채 남는다**(3번) |
| 4. 주문 저장 | `orderRepository.save(new Order(..))` (`:59`) | |
| 5. 주문 알림 | `sendOrderNotificationIfPossible` (`:62`, `:66-75`) | 카카오 액세스 토큰이 없으면 보내지 않는다. 예외는 모두 잡고 무시한다 |

## 2. 바뀔 작동

| 경우 | 지금 | 바뀐 뒤 |
|---|---|---|
| 포인트 부족 주문 | 500, 재고는 줄어든 채 남는다 | 500, 재고도 그대로다 |

**먼저 고쳐 실패시킬 테스트**: `order.feature` 16-2
- 시나리오 이름: `16-2. 포인트가 부족하면 500이 오지만 재고는 줄어든 채 남는다 (open-questions 3번)` → `16-2. 포인트가 부족하면 500이 오고 아무것도 바뀌지 않는다 (open-questions 3번)`
- 재고 기대값: `And 상품 1의 옵션 1 재고는 9다` → `And 상품 1의 옵션 1 재고는 그대로 10이다`
- 단계 정의(`OrderSteps.java:24`)가 "그대로"를 이미 받으므로 단계 정의는 바꾸지 않는다.
- 코드를 바꾸기 전에 이 테스트가 재고 단계(기대 10, 실제 9)에서 실패하는 것을 확인하고, 그 출력을 tasks.md에 남긴다.

**16-2가 500만 보지 않는지 확인한 결과**: 응답 코드 뒤에 상태 세 가지를 다시 조회한다.

| 단계 | 조회 방법 | 단계 정의 |
|---|---|---|
| `상품 1의 옵션 1 재고는 …` | `GET /api/products/1/options`의 옵션 1 `quantity` | `OrderSteps.java:24-35` |
| `user2의 포인트는 그대로 3,000,000이다` | DB `select point from member where email = ?` (회원 포인트 API가 없음, open-questions 4번) | `MemberSteps.java:32-37` |
| `user2의 주문 내역은 그대로 2건이다` | `GET /api/orders`의 `totalElements` | `OrderSteps.java:37-47` |

Given에서도 같은 세 단계로 시작 상태(재고 10, 포인트 3,000,000, 주문 내역 2건)를 확인한다.

## 3. 바뀌지 않아야 할 작동

| 작동 | 지키는 인수 테스트 |
|---|---|
| 정상 주문은 201, 응답 본문은 옵션·주문 수량·주문 메시지 | `order.feature` 16-1 |
| 정상 주문 뒤 재고 1 감소, 포인트 차감, 주문 내역 1건 증가 | `order.feature` 16-1 |
| 주문하면 그 주문이 주문 내역에 보인다 | `order-history.feature` 17-2 |
| 포인트 부족은 500, 포인트와 주문 내역은 그대로 | `order.feature` 16-2 |
| 재고 부족은 500, 재고·포인트·주문 내역 그대로 | `order.feature` 16-3 |
| 없는 옵션은 404, 포인트·주문 내역 그대로 | `order.feature` 16-4 |
| 틀린 로그인 토큰은 401, 재고 그대로 | `order.feature` 16-5 |
| 로그인 토큰 헤더가 없으면 400, 재고 그대로 | `order.feature` 16-6 |
| 주문 수량 0은 400, 재고·포인트·주문 내역 그대로 | `order.feature` 16-7 |
| 주문 내역은 자기 주문만 보인다 | `order-history.feature` 17-1 |
| 주문 내역 조회: 틀린 로그인 토큰은 401, 헤더가 없으면 400 | `order-history.feature` 17-3, 17-4 |

**테스트 없음**
- 201 응답의 `Location` 헤더(`/api/orders/{id}`, `OrderController.java:51`). 16-1은 본문만 본다.
- 카카오 액세스 토큰이 있는 회원에게 주문 알림을 보낸다. 카카오 서버에 기대서 인수 테스트가 없다.
- 카카오 액세스 토큰이 없으면 주문 알림을 보내지 않는다. 코드로만 판단했다(`OrderService.java:67-69`).
- 주문 알림이 실패해도 주문은 201로 성공한다(`OrderService.java:73-74`).

## 4. 알려진 한계 (07에서 아웃박스로 바꿀 때까지)

`createOrder` 전체에 트랜잭션을 걸면 주문 알림 호출(`:62`)도 트랜잭션 안에 들어간다.
- **외부 호출 동안 DB 연결을 잡고 있다.** 카카오 API 응답을 기다리는 동안 트랜잭션이 열려 있고 커밋도 늦어진다. 카카오가 느리면 연결 풀이 빨리 찬다.
- **알림 예외는 지금처럼 잡혀서 롤백되지 않는다.** `catch (Exception ignored)`(`:73-74`)가 그대로라, 알림이 실패해도 재고·포인트·주문은 커밋된다. 지금의 "알림이 실패해도 201"과 같다. 이 catch는 원래 있던 것이고, 4단계 규칙("예외를 삼키는 코드를 새로 만들지 않는다")에 따라 새로 늘리지 않는다.
- **open-in-view 설정**: `spring.jpa.open-in-view`를 따로 정하지 않아 기본값(켜짐)이다. 그래서 컨트롤러가 `authenticationResolver.extractMember`(`OrderController.java:41`)로 읽은 회원도 같은 영속성 컨텍스트에 있고, 요청이 끝날 때까지 그 컨텍스트가 열려 있다. 이번 작업에서 이 설정은 바꾸지 않는다.

## 5. 확인할 것

이번에 고칠지는 정하지 않는다.

- **주문 금액이 int 범위를 넘는 경우**: 주문 금액(`OrderService.java:54`)은 `int` 곱셈이다. 3,360,000원 × 640개 = 2,150,400,000은 int 최댓값 2,147,483,647을 넘는다.
  - 넘치면 음수(-2,144,567,296)가 되어 `deductPoint`의 "차감 금액은 1 이상이어야 합니다." 예외(`Member.java:57-59`)로 500이 될 것으로 보인다. 요청으로 확인하지 않았다.
  - 초기 데이터의 옵션 1 재고는 10이라 재고 부족(`Option.java:39-41`)이 먼저 걸린다. 재현하려면 재고가 640 이상인 옵션이 필요하다.
  - 주문 알림의 금액(`KakaoMessageClient.java:33`)도 같은 곱셈이다.
