# ADR-002: 비밀번호 암호화 전략

## 상태

채택됨 (2026-03-05)

## 맥락

회원의 비밀번호가 평문(`String`)으로 DB에 저장되고 있었다. `Member` 엔티티의 `password` 필드가 그대로 `member` 테이블의 `password` 컬럼에 들어가는 구조였다.

```java
// 기존: 평문 비교
if (member.getPassword() == null || !member.getPassword().equals(password)) {
    throw new IllegalArgumentException("이메일 또는 비밀번호가 올바르지 않습니다.");
}
```

DB 유출 시 모든 회원의 비밀번호가 노출되는 보안 위험이 있었다.

## 검토한 대안

### 1. Spring Security `PasswordEncoder` (BCrypt)

- 장점: 업계 표준, adaptive cost factor로 GPU 브루트포스 저항, Spring 생태계 통합
- 단점: Spring Security 의존성 추가 필요. 현재 프로젝트에 Spring Security가 없으며, 인증은 JWT + 커스텀 resolver로 처리 중

### 2. SCrypt / Argon2

- 장점: BCrypt보다 강력한 메모리-하드 해싱
- 단점: 추가 라이브러리 필요, 현재 단계에서 과도한 복잡성

### 3. SHA-256 + salt (`Password` 값 객체)

- 장점: JDK 표준 API만 사용, 외부 의존성 없음, 값 객체로 캡슐화하여 도메인 모델에 자연스럽게 통합
- 단점: SHA-256은 fast hash로 GPU 브루트포스에 상대적으로 취약

## 결정

**대안 3 — SHA-256 + salt 기반 `Password` 값 객체를 채택한다.**

현재 프로젝트는 학습/온보딩 목적이며, 평문 저장을 해소하는 것이 1차 목표이다. JDK 표준 API만으로 구현하여 외부 의존성을 추가하지 않는다.

### 구현 설계

```
Password (@Embeddable)
├── hash: String (password_hash 컬럼)
├── salt: String (password_salt 컬럼)
├── of(rawPassword) → 생성 (SecureRandom 16바이트 salt + SHA-256)
└── validate(rawPassword) → 검증 (동일 salt로 해시 비교)
```

- `Member` 엔티티: `String password` → `@Embedded Password password`
- 생성/수정 시 `Password.of(raw)`, 검증 시 `password.validate(raw)`
- Flyway `V3__Encrypt_member_password.sql`로 스키마 마이그레이션

## 결과

### 해결된 문제
- 비밀번호가 해시+salt로 저장되어 DB 유출 시 원문 복원 불가
- 암호화 로직이 `Password` 값 객체에 캡슐화되어 `Member`와 `MemberService`가 암호화 세부사항을 알지 않음
- 값 객체 패턴으로 도메인 모델의 표현력 향상 (`String password` → `Password password`)

### 수용한 트레이드오프
- SHA-256은 BCrypt/Argon2 대비 브루트포스에 취약하다. 프로덕션 전환 시 `Password` 값 객체 내부만 BCrypt로 교체하면 되므로, 외부 인터페이스 변경 없이 전환 가능하다.
- 기존 V2 시드 데이터의 회원(평문 비밀번호)은 마이그레이션 후 로그인 불가. 시드 데이터이므로 수용.
- 테스트에서 SQL로 회원을 직접 INSERT할 수 없게 되어, API 기반 회원 등록으로 전환 필요.
