# 0002. 카카오 주문 알림을 아웃박스에 저장하고 커밋 뒤 보내며 실패하면 5번까지 다시 보낸다

- 날짜: 2026-11-27
- 상태: 채택
- 관련: [`docs/open-questions.md`](../open-questions.md) 10번, 14번 / [`docs/work/07-order-notification-outbox/tech-spec.md`](../work/07-order-notification-outbox/tech-spec.md) / [ADR 0001](0001-order-transaction-boundary.md)

## 맥락

- ADR 0001로 `OrderService.createOrder`가 한 트랜잭션이 되면서, 카카오 주문 알림 호출도 트랜잭션 안에 들어갔다. 카카오 응답을 기다리는 동안 트랜잭션이 열려 있었다.
- 알림 예외는 모두 잡고 무시했다(`catch (Exception ignored)`). 실패를 기록하지 않았고, 다시 보내지도 않았다(open-questions 10번).

## 결정

- **아웃박스**: 카카오 액세스 토큰이 있는 회원의 주문이면, 주문과 같은 트랜잭션에 `order_notification` 행을 "보낼 것"(PENDING)으로 저장한다. 저장하는 것은 주문 시점의 알림 문구와 회원 번호다. 카카오 액세스 토큰은 저장하지 않고 보낼 때 회원에서 읽는다. 주문이 롤백되면 알림도 함께 롤백된다.
- **커밋 직후 발송**: `@TransactionalEventListener(AFTER_COMMIT)`(`OrderNotificationRelay`)가 요청과 같은 스레드에서 한 번 보낸다. 결과는 새 트랜잭션(`OrderNotificationDispatcher`, `REQUIRES_NEW`)에서 저장한다. 성공하면 "보냄"(SENT)과 보낸 시각을, 실패하면 시도 횟수 +1과 마지막 오류를 저장하고 warn 로그를 남긴다.
- **재시도**: 실패한 것만 주기 작업이 다시 보낸다. 5번까지 보내고, 다섯 번 실패하면 "실패"(FAILED)로 표시해 더 보내지 않는다. (B2에서 넣는다)
- **응답 코드**: 바꾸지 않는다. 알림이 실패해도 주문은 201이다.

## 고려한 선택지

| 선택지 | 고르지 않은 이유 |
|---|---|
| 트랜잭션 안에서 바로 보내기(지금) | 카카오를 기다리는 동안 트랜잭션이 열려 있고, 실패하면 알림이 사라진다 |
| 커밋 직후 발송을 `@Async`로 다른 스레드에서 | 응답은 빨라지지만, 테스트가 발송을 기다려야 해서 새 라이브러리나 테스트용 실행기 설정이 필요하다. 스레드 풀이 찼을 때의 처리도 정해야 한다(tech-spec 6장) |
| 커밋 직후에 보내지 않고 주기 작업만으로 보내기 | 정상인 경우에도 알림이 주기 간격만큼 늦게 간다 |

## 결과

- 알림 발송이 트랜잭션 밖(커밋 뒤)으로 나가고, 실패가 시도 횟수와 마지막 오류로 남는다(`order-notification.feature` 16-8~16-11).
- **ADR 0001의 두 문제가 풀린다**
  - "주문 알림 호출이 07(아웃박스) 전까지 트랜잭션 안에 있다": 발송이 커밋 뒤로 나간다.
  - "알림 예외는 지금처럼 잡혀서 롤백되지 않는다": 예외를 무시하지 않고 시도 횟수와 마지막 오류로 남긴다.
- **생기는 문제**
  - 주문 응답이 카카오 응답을 기다린다. 커밋 직후 발송은 요청과 같은 스레드라, 카카오가 느리면 주문 응답도 느리다. 응답 시간이 문제가 되면 `@Async`로 바꾸는 새 ADR을 쓴다.
  - 같은 알림이 두 번 갈 수 있다. 카카오에는 보냈는데 "보냄"으로 저장하기 전에 실패하면(앱 종료, DB 오류), 행이 "보낼 것"으로 남아 재시도가 다시 보낸다. 카카오 "나에게 보내기"에는 중복을 막는 키가 없다.
  - 앱이 여러 대면 재시도가 겹친다. 행을 잠그지 않아서, 두 대가 같은 "보낼 것" 행을 동시에 보낼 수 있다. 지금은 한 대로 운영한다고 본다.
  - 커밋 직후 발송이 1분 넘게 걸리면 재시도(`created_at`이 1분보다 오래된 시도 0번 행)와 겹쳐 두 번 보낼 수 있다.
  - open-in-view가 켜져 있어 커밋 직후 발송 동안 요청의 DB 연결과 REQUIRES_NEW의 연결을 함께 잡을 수 있다(확인하지 않음).
