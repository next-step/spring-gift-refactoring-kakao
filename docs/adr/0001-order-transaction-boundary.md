# 0001. 주문의 재고·포인트·주문 저장을 한 트랜잭션으로 묶고 응답 코드는 500으로 유지한다

- 날짜: 2026-11-27
- 상태: 채택
- 관련: [`docs/open-questions.md`](../open-questions.md) 3번, 12번 / [`docs/work/06-order-transaction/tech-spec.md`](../work/06-order-transaction/tech-spec.md)

## 맥락

- 주문하기(`OrderService.createOrder`)는 재고 차감, 포인트 차감, 주문 저장을 따로 커밋했다.
- 그래서 포인트가 부족하면 500이 오지만 재고는 줄어든 채 남았다(open-questions 3번).
- 재고 부족은 저장 전에 실패해서 상태가 남지 않았다(12번). 같은 500이어도 실패한 단계에 따라 데이터가 남기도 하고 남지 않기도 했다.

## 결정

- **트랜잭션 경계**: `OrderService.createOrder` 메서드에 `@Transactional`을 붙인다. 옵션 확인부터 주문 알림 호출까지 한 트랜잭션이다. 클래스와 `findOrders`에는 붙이지 않는다.
- **응답 코드**: 포인트 부족과 재고 부족 모두 지금처럼 500을 유지한다. 이번 작업은 "실패하면 아무것도 바뀌지 않는다"만 바꾼다.

## 고려한 선택지

| 선택지 | 고르지 않은 이유 |
|---|---|
| 포인트 부족, 재고 부족을 400으로 바꾸기 | 응답 코드까지 바꾸면 한 커밋에 작동 변경이 둘이 된다. 클라이언트가 보는 계약이 바뀌므로 따로 정한다 |
| `@Transactional` 없이, 포인트 차감이 실패하면 재고를 직접 되돌리는 보상 코드 | 단계가 늘 때마다 되돌릴 코드도 늘고, 되돌리는 중에 실패하면 상태가 어긋난다 |

## 결과

- 포인트가 부족한 주문은 500이 오고 재고·포인트·주문 내역이 모두 그대로다(`order.feature` 16-2).
- **생기는 문제**
  - 서버 오류와 주문 거절(포인트 부족, 재고 부족)을 응답 코드로 구분할 수 없다. 둘 다 500이다.
  - 주문 알림 호출이 07(아웃박스) 전까지 트랜잭션 안에 있다. 카카오 응답을 기다리는 동안 DB 연결을 잡고 있고, 커밋도 늦어진다. (07에서 풀림, ADR 0002)
  - 알림 예외는 지금처럼 잡혀서 롤백되지 않는다. (07에서 풀림, ADR 0002)
