# ADR-003: 위시 중복 등록 방지 전략 — DB 유니크 제약 vs 애플리케이션 레벨 제어

## 상태
승인됨

## 맥락
`WishService.addWish()`에서 `findByMemberIdAndProductId()` 조회 후 `save()`를 호출하는 사이에
동시 요청이 들어오면 중복 위시가 생성될 수 있다. (조회 → 판단 → 저장이 원자적이지 않음)

## 선택지

### A. 애플리케이션 레벨 동기화 (synchronized / 비관적 락)
- 서비스 메서드에 `synchronized` 또는 비관적 락 적용
- 장점: 코드 레벨에서 제어 가능
- 단점: `synchronized`는 다중 인스턴스에서 무력화. 비관적 락은 위시 테이블 전체에 거는 것이 어려움

### B. DB 유니크 제약 조건 (`member_id`, `product_id`)
- 테이블에 유니크 인덱스 추가, 중복 시 DB가 거부
- 장점: 다중 인스턴스에서도 안전, 근본적 방지, 성능 부담 거의 없음
- 단점: 예외 처리 필요 (`DataIntegrityViolationException`)

## 결정
**B. DB 유니크 제약 조건**을 선택한다.

## 근거
- 중복 방지는 데이터 정합성 문제이므로 DB 레벨에서 보장하는 것이 가장 안전하다.
- 애플리케이션 레벨 동기화는 서버가 여러 대일 때 무력화되므로 근본적 해결이 아니다.
- Flyway 마이그레이션으로 유니크 제약을 추가한다.

## 검증 방법
- 동일한 `(memberId, productId)` 조합으로 위시 등록 시 중복 저장되지 않는지 확인
