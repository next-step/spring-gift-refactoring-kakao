# ADR-001: 외부 API 호출의 트랜잭션 분리 전략

## 상태

채택됨 (2026-03-05)

## 맥락

`OrderService.placeOrder()`는 하나의 `@Transactional` 안에서 다음을 수행했다:

1. 재고 차감 (`option.subtractQuantity`)
2. 포인트 차감 (`member.deductPoint`)
3. 주문 저장 (`orderRepository.save`)
4. **카카오 메시지 전송** (`kakaoMessageClient.send`) — 외부 HTTP 호출

4번이 트랜잭션 내부에 있어 두 가지 문제가 발생했다:

- **롤백 위험**: 1~3이 모두 성공해도 카카오 API 실패 시 전체 롤백. `@Retryable`(3회, 500ms 간격)로 최대 1.5초간 재시도하다 실패하면 주문 자체가 취소됨.
- **커넥션 점유**: 외부 API 응답을 기다리는 동안 DB 커넥션과 행 락을 계속 점유. 카카오 API 지연 시 커넥션 풀 고갈 가능.

## 검토한 대안

### 1. 컨트롤러에서 직접 호출

```
Controller: order = service.placeOrder() → kakaoClient.send()
```

- 장점: 단순함
- 단점: 컨트롤러에 `Member`, `Option` 객체와 `KakaoMessageClient` 의존성이 노출됨. 서비스가 반환해야 할 정보가 늘어남.

### 2. `TransactionSynchronizationManager.afterCommit` 콜백

```java
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            kakaoMessageClient.send(member, saved, option);
        }
    });
```

- 장점: 서비스 안에서 완결, 추가 클래스 불필요
- 단점: 익명 클래스가 장황하고, 발행-구독 의도가 코드에 드러나지 않음

### 3. `@TransactionalEventListener` 이벤트 방식

```java
// 서비스
eventPublisher.publishEvent(new OrderCompletedEvent(member, saved, option));

// 리스너
@TransactionalEventListener
public void handle(OrderCompletedEvent event) { ... }
```

- 장점: 관심사 분리 명확, 코드 가독성 우수, 리스너 추가/교체 용이
- 단점: 이벤트 record + 리스너 클래스 추가 필요

## 결정

**대안 3 — `@TransactionalEventListener` 이벤트 방식을 채택한다.**

- `OrderCompletedEvent` record를 발행하고, `OrderCompletedEventListener`가 커밋 후 메시지를 전송한다.
- `@TransactionalEventListener`의 기본 phase가 `AFTER_COMMIT`이므로 트랜잭션 성공 시에만 실행된다.
- `OrderService`는 `KakaoMessageClient` 의존성을 갖지 않고, `ApplicationEventPublisher`만 사용한다.

## 결과

### 해결된 문제
- 카카오 API 실패가 주문 트랜잭션에 영향을 주지 않음
- 외부 API 대기 중 DB 커넥션/락 점유 없음
- 메시지 전송 관심사가 서비스에서 분리됨

### 수용한 트레이드오프
- 메시지 전송 실패 시 주문은 성공하지만 알림이 누락될 수 있음. 현재는 `@Retryable`(3회)과 실패 로깅으로 대응하며, 향후 필요시 메시지 큐(outbox 패턴) 도입을 검토한다.
- 이벤트 record와 리스너 클래스가 추가되어 파일 수가 늘어남. 그러나 각 클래스의 역할이 단일하여 유지보수에 유리하다.
