# ADR 008: 위시리스트 기본 정렬 전략

> 작성일: 2026-03-05
> 상태: Accepted

## Context (맥락)

위시리스트에 `created_at` 컬럼이 추가되면서, 클라이언트가 정렬 조건을 지정하지 않았을 때(unsorted Pageable) 기본 정렬을 어디서, 어떻게 적용할지 결정이 필요했다.

## 선택지

| 선택지 | 설명 | 장점 | 단점 |
|--------|------|------|------|
| **A. 서비스 레이어에서 기본 정렬 주입** | `WishService.findByMemberId`에서 unsorted일 때 `Sort.by(DESC, "createdDate")` 적용 | 비즈니스 의도가 서비스에 명시됨. 클라이언트가 정렬을 지정하면 그대로 존중 | 서비스가 Pageable을 조작하는 책임을 가짐 |
| B. Repository `@Query` + `ORDER BY` | 쿼리 자체에 기본 정렬을 하드코딩 | 항상 일관된 정렬 보장 | 클라이언트 지정 정렬을 무시하거나 충돌 가능. 유연성 부족 |
| C. Controller에서 `@SortDefault` | `@PageableDefault(sort = "createdDate", direction = DESC)` 사용 | Spring MVC 네이티브 방식 | 표현 계층에 비즈니스 정렬 규칙이 위치함. 다른 진입점(배치 등)에서 누락 가능 |

## Decision (결정)

**선택지 A: 서비스 레이어에서 기본 정렬 주입**을 채택한다.

```java
if (pageable.getSort().isUnsorted()) {
    pageable = PageRequest.of(pageable.getPageNumber(), pageable.getPageSize(),
        Sort.by(Sort.Direction.DESC, "createdDate"));
}
```

- 클라이언트가 명시적으로 정렬을 지정하면 그대로 사용한다.
- unsorted일 때만 서비스가 비즈니스 기본값을 적용한다.
- 이 패턴은 다른 도메인(주문 목록 등)에서도 동일하게 적용할 수 있다.

## Consequences (결과)

### Pros
- 비즈니스 기본 정렬 규칙이 서비스 레이어에 캡슐화되어 진입점에 무관하게 적용된다
- 클라이언트 지정 정렬을 존중하면서도 기본값을 보장한다
- 단위 테스트에서 `argThat`으로 정렬 조건 적용 여부를 검증할 수 있다

### Cons
- 서비스가 Pageable 객체를 재구성하는 책임을 가진다
- 기본 정렬이 필요한 서비스마다 동일 패턴을 반복해야 한다
