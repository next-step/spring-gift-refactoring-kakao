# 0001. 트랜잭션 경계 변경의 구조/작동 분류 기준

## 상태

accepted

## 컨텍스트

Phase 6(트랜잭션 경계 세우기)에서 Service 메서드의 `@Transactional`을 검증하고 개선해야 한다.
이 과제는 구조 변경과 작동 변경을 엄격히 분리하여 커밋할 것을 요구한다.

그런데 트랜잭션 경계 변경은 단순히 하나의 카테고리로 분류할 수 없다.
선언 위치를 옮기는 것은 외부 동작에 영향이 없지만,
복합 쓰기 연산에 원자성을 부여하면 실패 시 롤백 범위가 달라져 관찰 가능한 상태가 변경된다.

트랜잭션 변경을 어떤 기준으로 구조/작동으로 분류할지 결정이 필요하다.

## 선택지

### 선택지 1: 일괄 구조 변경으로 분류

모든 `@Transactional` 추가/변경을 `refactor` 커밋으로 처리한다.

- 장점: 단순하다. 커밋 수가 적고 작업 흐름이 간결하다.
- 단점: 복합 쓰기에 원자성을 부여하는 변경은 실패 시 부분 반영 → 전체 롤백으로 동작이 달라지는데, 이를 구조 변경으로 분류하면 작동 변경 증거(상태 재조회 테스트)가 누락된다.

### 선택지 2: 변경 유형별 구조/작동 분리

트랜잭션 변경을 실제 동작 영향에 따라 분류하고, 각각 별도 커밋으로 처리한다.

- 장점: 구조 변경과 작동 변경의 정의에 충실하다. 작동 변경에는 상태 재조회 테스트가 동반되어 변경 사실이 증명된다.
- 단점: 커밋 수가 늘어나고, 각 변경의 분류를 판단하는 비용이 발생한다.

## 결정

**선택지 2: 변경 유형별 구조/작동 분리**를 채택한다.

분류 기준은 "해당 변경으로 인해 관찰 가능한 상태가 달라지는가?"이다.

| 변경 내용 | 분류 | 커밋 타입 | 이유 |
|---|---|---|---|
| 선언 위치 이동 (메서드→클래스) | 구조 변경 | `refactor` | 동작 동일 |
| 단일 Repository 호출에 명시적 추가 | 구조 변경 | `refactor` | 이미 암묵적 트랜잭션 존재 |
| 복합 쓰기에 원자성 부여 | 작동 변경 | `feat` | 실패 시 롤백 동작이 달라짐 |
| propagation/isolation 변경 | 작동 변경 | `feat` | 동시성·참여 동작 변경 |
| readOnly 추가 (쓰기 없는 메서드) | 구조 변경 | `refactor` | 최적화 힌트, 동작 동일 |
| readOnly 추가 (쓰기 있는 메서드) | 작동 변경 | `feat` | 쓰기 시 예외 발생 가능 |

핵심 근거: 커밋 수 증가 비용보다, 작동 변경에 증거 테스트를 누락하는 위험이 더 크다.

## 결과

- Phase 6에서 트랜잭션 변경 시 매번 위 분류 표를 참조하여 커밋을 분리한다.
- 구조 변경 커밋은 기존 테스트 통과로 검증한다.
- 작동 변경 커밋은 변경 전 3줄 명세를 작성하고, 상태 재조회 테스트를 동반한다.
- 이 기준은 Phase 6 이후의 트랜잭션 관련 변경에도 동일하게 적용한다.
