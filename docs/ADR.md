## 1. 외부 API 호출을 트랜잭션에서 분리

- **상태**: 채택
- **일자**: 2026-03-05

### 맥락

OrderService.create()는 재고 차감, 포인트 차감, 주문 저장, 위시 정리, 카카오톡 메시지 발송을 하나의 `@Transactional` 안에서 수행했다. 카카오 API 서버에 장애가 발생하거나 응답이 지연되면 트랜잭션과 DB 커넥션이 불필요하게 오래 점유되어 전체 서비스 성능에 영향을 줄 수 있다.

### 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **트랜잭션 내 직접 호출** (기존) | 구현이 단순함 | API 지연 시 DB 커넥션 점유, 트랜잭션 타임아웃 위험 |
| **@TransactionalEventListener** | 트랜잭션 커밋 후 실행, 스프링 내장 기능, 동기 실행으로 디버깅 용이 | 이벤트 클래스 추가 필요 |
| **@Async** | 비동기 실행으로 응답 속도 개선 | 스레드풀 관리 필요, 에러 추적 어려움, 테스트 복잡 |

### 결정

`@TransactionalEventListener(phase = AFTER_COMMIT)`를 사용한다.

- `OrderCompletedEvent`를 발행하고, `OrderNotificationListener`가 트랜잭션 커밋 후 메시지를 발송한다.
- 메시지 발송 실패는 주문에 영향을 주지 않는다 (best-effort).

### 적용 규칙

- 트랜잭션 안에서 외부 시스템(API, 메시징 등)을 호출하지 않는다.
- 외부 호출이 필요하면 이벤트를 발행하고, 리스너에서 트랜잭션 커밋 후 처리한다.
- 외부 호출 실패가 핵심 로직에 영향을 주지 않아야 한다.

### 결과

- 카카오 API 지연이 주문 트랜잭션과 DB 커넥션에 영향을 주지 않는다.
- OrderService가 MessageClient에 직접 의존하지 않아 테스트가 단순해진다.
- 향후 알림 채널 추가 시 리스너만 추가하면 된다.

## 2. 서비스 반환값 규칙 — null/enum 대신 예외

- **상태**: 채택
- **일자**: 2026-03-05

### 맥락

기존 서비스 메서드들은 엔티티를 찾지 못하거나 비정상 상태일 때 null을 반환하거나 enum(WishDeleteResult)을 반환했다. 컨트롤러에서는 매번 null 체크나 switch 분기를 수행해야 했고, 실수로 체크를 누락하면 NullPointerException이 발생했다.

### 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **null 반환 + 컨트롤러 체크** (기존) | 명시적 흐름 제어 | null 체크 누락 위험, 컨트롤러 코드 비대화 |
| **enum 반환 + switch 분기** (기존 Wish) | 가능한 결과를 타입으로 표현 | 서비스-컨트롤러 결합, 새 상태 추가 시 양쪽 수정 |
| **예외 + @ExceptionHandler** | 컨트롤러 단순화, 일관된 에러 처리 | 예외를 흐름 제어에 사용하는 비용 |

### 결정

서비스에서 실패 시 예외를 던지고, 컨트롤러에서 `@ExceptionHandler`로 HTTP 응답을 매핑한다.

- `NoSuchElementException` → 404 Not Found
- `IllegalArgumentException` → 400 Bad Request
- `IllegalStateException` → 403 Forbidden

### 적용 규칙

- 서비스 메서드는 null을 반환하지 않는다. `orElseThrow`를 사용한다.
- 서비스 메서드는 결과 분기용 enum을 반환하지 않는다. 비정상 상태는 예외로 처리한다.
- 컨트롤러에서 서비스 반환값에 대한 null 체크를 하지 않는다.
- 예외 타입별 HTTP 상태 코드 매핑은 `@ExceptionHandler`로 일관되게 처리한다.

### 결과

- 컨트롤러 코드가 간결해지고, null 체크 누락으로 인한 버그가 사라진다.
- 서비스의 예외 타입과 HTTP 응답 코드 매핑이 한 곳에서 관리된다.
- 모든 서비스(Member, Category, Product, Option, Order, Wish)에 동일 규칙이 적용되어 일관성이 확보된다.

## 3. 외부 시스템 연동 인터페이스 추상화

- **상태**: 채택
- **일자**: 2026-03-05

### 맥락

카카오 로그인(KakaoLoginClient)과 카카오 메시지 발송(KakaoMessageClient)이 서비스에 직접 주입되어 있었다. 서비스가 카카오라는 특정 구현에 결합되어 있어, 프로바이더 교체/추가 시 서비스 코드를 수정해야 했고, 테스트에서 외부 API를 모킹하기 어려웠다.

### 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **구현체 직접 의존** (기존) | 단순하고 즉시 이해 가능 | 프로바이더 변경 시 서비스 수정, 테스트 모킹 어려움 |
| **인터페이스 추상화** | 확장 용이, 테스트 용이, 서비스 변경 없이 구현체 교체 | 인터페이스 + 구현체 파일 분리 필요 |

### 결정

외부 시스템 연동 시 인터페이스를 도입하고, 구현체를 스프링 빈으로 주입한다.

적용된 사례:
- `OAuthClient` 인터페이스 ← `KakaoOAuthClient` 구현
- `MessageClient` 인터페이스 ← `KakaoMessageClient` 구현

### 적용 규칙

- 외부 시스템(OAuth, 메시징, 결제 등)과의 연동은 반드시 인터페이스를 통해 수행한다.
- 서비스는 인터페이스에만 의존하고, 구현체를 직접 참조하지 않는다.
- 인터페이스 메서드명은 특정 프로바이더에 종속되지 않는 이름을 사용한다.
  - `sendKakaoMessage` (X) → `sendOrderMessage` (O)
  - `getKakaoAuthUrl` (X) → `getAuthorizationUrl` (O)

### 결과

- 새로운 OAuth 프로바이더(네이버, 구글 등) 추가 시 구현체만 만들면 된다.
- 테스트에서 외부 API 없이 모킹으로 검증할 수 있다.
- 서비스 코드가 특정 외부 시스템에 종속되지 않는다.
