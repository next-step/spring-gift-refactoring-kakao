# 판단근거

## 구조 변경 vs 작동 변경 판단 기준

### 정의
- **구조 변경**: 코드를 다른 클래스/계층으로 이동하되, 분기·예외·반환 흐름은 그대로 유지하는 것
- **작동 변경**: 분기 조건, 예외 흐름, 반환 값 등 로직의 흐름 자체가 달라지는 것

### 적용 예시: orElse(null) → orElseThrow
기존 Controller에서 `orElse(null)` + null 체크로 404를 반환하던 코드를 Service로 옮기면서 `orElseThrow` + try-catch로 바꾼 적이 있음.
HTTP 응답(404)은 동일하지만, 내부 흐름이 null 분기에서 예외 분기로 바뀌었으므로 **작동 변경에 해당**.
코드 리뷰 피드백을 반영하여 OrderService는 기존 null 패턴으로 복원함.

### 원칙
1단계에서는 구조 변경만 수행하고, 작동 변경은 섞지 않는다.
Service 추출 시 기존 Controller의 분기/예외/반환 흐름을 그대로 유지해야 순수한 구조 변경이다.

## 서비스 계층 추출

### 추출 순서: 복잡한 컨트롤러부터

**복잡도 기준**: 비즈니스 로직 라인 수 + 의존성(Repository/외부 API) 수
- OrderController: 5단계 흐름(옵션 검증→재고 차감→포인트 차감→주문 저장→카카오 알림), 의존성 4개 → 가장 복잡
- CategoryController: 단순 CRUD 위임, 의존성 1개 → 가장 단순

**복잡한 것부터 진행한 이유**:
- 복잡한 컨트롤러에서 추출 패턴(에러 전달 방식, 트랜잭션 경계 등)을 먼저 확립하고, 나머지는 그 패턴을 따라가는 방식
- 리스크가 큰 작업을 앞에 배치해서 문제를 조기에 발견

**반대(단순한 것부터)의 장점**:
- 위험이 적은 곳에서 연습하고 패턴을 익힌 뒤 복잡한 곳에 적용할 수 있음

어느 쪽이 절대적으로 우월하진 않지만, 이번에는 패턴 확립 우선 방식을 선택함.

### OrderController -> OrderService
Controller에 옵션 검증, 재고 차감, 포인트 차감, 주문 저장, 카카오 알림이 전부 들어있었음.
이건 하나의 트랜잭션으로 묶여야 하는 도메인 로직이라서 Service로 옮김.
Controller는 인증 확인 + Service 호출 + HTTP 응답 변환만 담당.
옵션 미존재 시 기존 Controller의 `orElse(null)` + null 체크 패턴을 그대로 유지.
Service는 옵션이 없으면 null을 반환하고, Controller에서 null 체크 후 404 반환.
(초기에는 `orElseThrow`로 변경했으나, 코드 리뷰에서 작동 변경에 해당한다는 피드백을 받아 복원)

### MemberController -> MemberService
이메일 중복 검사, 회원 생성, 비밀번호 비교, 토큰 발급이 Controller에 있었음.
회원 가입 규칙이랑 인증 로직은 HTTP 계층이랑 상관없는 도메인 규칙이니까 Service로 옮김.

### KakaoAuthController -> KakaoAuthService
OAuth URL 생성, 토큰 교환, 사용자 정보 조회, 회원 자동 등록, 토큰 관리 전부 Controller에 있었음.
외부 API 호출이랑 회원 등록 로직은 도메인 로직이니까 Service로 옮김.

### OptionController -> OptionService
옵션명 검증, 중복 검사, "상품에 옵션 1개 이상 있어야 한다"는 제약이 Controller에 있었음.
도메인 불변 규칙이니까 Service로 옮김.

### WishController -> WishService
상품 존재 확인, 중복 위시 방지, 소유자 권한 확인이 Controller에 있었음.
도메인 규칙이니까 Service로 옮김.
addWish의 200(기존)/201(신규) 응답 구분을 위해 `AddWishResult` 레코드 사용.

### ProductController / AdminProductController -> ProductService
상품명 검증이랑 카테고리 검증이 두 컨트롤러에서 중복되고 있었음.
Service로 뽑아서 공유. API는 `allowKakao=false`, Admin은 `allowKakao=true`로 기존 동작 유지.
Admin의 폼 렌더링 로직은 프레젠테이션이니까 Controller에 남김.

### AdminMemberController -> MemberService 재사용
이메일 중복 검사가 MemberController.register()랑 똑같은 로직이었음.
MemberService에 Admin용 메서드(getAllMembers, getMember, createMember, updateMember, chargePoint, deleteMember) 추가해서 재사용.

### CategoryController -> CategoryService
비즈니스 로직은 거의 없지만 프로젝트 전체의 Controller-Service 패턴 일관성을 위해 추출.

## 트랜잭션 경계

### 카카오 알림과 트랜잭션 분리

**문제:** OrderService.createOrder()에 @Transactional을 추가하면, 카카오 외부 API 호출이 트랜잭션 안에서 실행됨. 외부 API 응답을 기다리는 동안 DB 커넥션을 불필요하게 점유 → 동시 주문 시 커넥션 풀 부족 위험.

**선택지:**
- A. 메서드 분리: Controller에서 createOrder() 후 sendNotification() 별도 호출
- B. @TransactionalEventListener: 트랜잭션 커밋 후 이벤트로 알림 발송

**선택:** A (메서드 분리)
**이유:**
- 카카오 알림은 이미 best-effort (catch Exception ignored)로 구현되어 있어 알림 실패가 트랜잭션 롤백을 유발하지 않음
- 롤백 문제가 아니라 커넥션 점유가 핵심 문제이므로, 메서드 분리만으로 충분히 해결됨
- 현재 프로젝트 규모에서 이벤트 구조 도입은 과도함
- B는 "커밋 후에만 알림"이라는 의미적 안전성이 있지만, 현재 코드에서 알림은 맨 마지막에 호출되고 실패해도 무시하므로 실질적 차이 없음

## 도메인 책임 되찾기

### 계층별 책임 정의

리팩터링 기준을 세우기 위해 프로젝트 계층별 역할을 정의했다.

| 계층 | 역할 | 들어가야 할 것 | 들어가면 안 되는 것 |
|------|------|---------------|-------------------|
| Entity | 도메인 규칙의 주인 | 불변식 검증, 상태 변경, 계산, 자기 데이터에 대한 판단 | HTTP, Repository 호출, 외부 API |
| Repository | 저장/조회 | JPA 쿼리 정의 | 비즈니스 로직, 계산 |
| Service | 유스케이스 조율 | 트랜잭션 경계, Entity 간 협력 조율, Repository 호출 순서 | HTTP 응답 결정, Entity가 할 수 있는 계산/판단 |
| Controller | HTTP 경계 | 요청 파싱, 인증 확인, Service 호출, 응답 변환 | 비즈니스 로직, 도메인 판단 |

**핵심 판단 기준:** Entity가 자기 데이터로 할 수 있는 일을 Service가 대신하고 있으면 책임 누수.

### orElse(null) → orElseThrow 변환을 "도메인 책임 되찾기"에서 제외한 이유

기존 plan에 있던 "orElse(null) → orElseThrow + 에러 처리(500→400)" 항목을 검토했다.

- OrderService의 `orElse(null)` + Controller의 null 체크 패턴은 "Service 결과 → HTTP 응답 매핑"이라는 Controller의 정당한 역할이다.
- 엔티티 존재 검증은 이미 Service에 있고, Controller의 null 체크는 HTTP 응답 변환일 뿐 "책임 누수"가 아니다.
- 500→400 에러 처리 개선은 실질적 가치가 있지만, "작동을 유지하면서 책임을 이동"이라는 요구사항과 맞지 않는다 (에러 응답이 500에서 400으로 바뀌므로 작동 변경).
- 따라서 이 항목은 "도메인 책임 되찾기"가 아니라 "에러 처리 개선"에 해당하므로 제외했다.

### 도메인별 책임 분석 결과

프로젝트 전체 Entity와 Service를 분석하여 책임 누수를 식별했다.

**이미 잘 되어 있는 것:**
- Member.deductPoint() / chargePoint() — Entity가 포인트 불변식(>= 0)을 지킴
- Option.subtractQuantity() — Entity가 재고 불변식(>= 0)을 지킴

**책임 누수가 확인된 것:**
- 가격 계산: OrderService가 `option.getProduct().getPrice() * quantity` 수행 → Option의 계산 책임
- 이름 검증: OptionNameValidator / ProductNameValidator라는 별도 클래스에 분리되어 Service가 호출 → Entity의 불변식 책임

**검토했으나 제외한 것:**
- Wish 소유자 검증 (`wish.getMemberId().equals(memberId)`): Order는 `findByMemberId`로 사전 필터링, Wish 삭제는 `wishId`로 조회 후 사후 검증. 상황이 달라서 다른 방식을 쓰는 것이지 일관성 문제가 아님. `wish.isOwnedBy(memberId)` 메서드를 만들 수 있지만 한 줄 equals를 감싸는 것이라 개선 효과가 크지 않음.

## ADR (Architecture Decision Record)

### ADR-1: 가격 계산 로직을 Option 도메인으로 이동

**상황:** OrderService.createOrder()에서 `option.getProduct().getPrice() * request.quantity()`로 가격을 계산하고 있음.

**선택지:**
- A. Option에 `calculatePrice(int quantity)` 메서드 추가 — 내부에서 `this.product.getPrice() * quantity`
- B. Product에 `calculatePrice(int quantity)` 메서드 추가 — 호출부는 `option.getProduct().calculatePrice(qty)`로 체이닝 잔존
- C. 현행 유지 — Service에서 계산

**선택:** A
**이유:**
- 주문은 Option 단위로 발생하고, 현실적으로 Option별 가격이 다를 수 있음 (현재 설계에서 price가 Product에만 있는 것은 한계)
- Option이 price를 캡슐화하면 나중에 Option에 price 필드가 생겨도 호출부(OrderService) 변경 없음
- B는 체이닝이 남아서 호출부 단순화 효과가 없음
- 기존 패턴(Option.subtractQuantity)과 일관성 유지 — Option이 자기 관련 연산을 소유

**트레이드오프:** Option이 Product의 price에 의존하는 구조가 캡슐화될 뿐, 의존 자체가 사라지지는 않음.

### ADR-2: 이름 검증을 Entity 생성자/update로 이동

**상황:** OptionNameValidator, ProductNameValidator라는 별도 static 클래스에서 이름 규칙을 검증하고, Service가 이를 호출함. 반면 Member.deductPoint(), Option.subtractQuantity()는 Entity 내부에서 자기 불변식을 검증함. 같은 프로젝트 안에서 불변식 검증 위치가 불일치.

**선택지:**
- A. Entity 불변식(null, 길이, 특수문자)만 Entity로 이동. "카카오" 정책은 Service에 잔류.
- B. "카카오" 포함 모든 검증을 Entity로 이동. 생성자에 `allowKakao` 파라미터 추가.

**선택:** A
**이유:**
- Entity 불변식: 누가 호출하든 항상 참이어야 하는 것 (null, 길이, 특수문자)
- 정책: 호출자/맥락에 따라 달라지는 것 ("카카오" 제한은 API는 금지, Admin은 허용)
- B는 `allowKakao`가 Product의 상태가 아닌데 생성자 파라미터로 들어감 — 저장하지도 않고 검증에만 쓰고 버리는 파라미터가 됨
- Member 비유: "포인트 >= 0"은 Entity 불변식, "포인트 충전은 관리자만 가능"은 Service 정책 — 같은 구분

**검증 시점:** name이 설정되는 모든 진입점에서 검증
- Option: 생성자만 (name setter/update 없음)
- Product: 생성자 + update() 메서드 (private validateName 공유)

**트레이드오프:**
- Service에 카카오 검증이 남아서 검증이 두 곳에 분산됨 (Entity: 형식, Service: 정책)
- 하지만 이 분산은 의도적이고 각 계층의 책임에 맞음
- NameValidator 클래스를 삭제하므로 파일 수 감소
