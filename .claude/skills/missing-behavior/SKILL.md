# 누락된 작동 구현

## 목표
기존 코드에 의도가 남아 있었지만 구현되지 않은 작동을 찾아 완료한다. **새로운 작동은 반드시 테스트 또는 검증 가능한 증거로 확인한다.**

## 대상 범위
프로젝트의 모든 프로덕션 코드 (엔티티, 서비스, 컨트롤러 등)

## 탐색 항목

아래 카테고리를 순서대로 전체 대상 범위에서 탐색한다.

### 1. 방어 로직 비대칭
- 동일한 패턴의 메서드 중 일부에만 입력값 검증(0 이하, null 등)이 있고 나머지에는 빠져 있는 경우
- 탐색 방법: 차감/증감/변경 메서드를 쌍으로 비교하여 검증 유무를 확인

### 2. 정의만 있고 미사용인 메서드 (의도가 남아 있는 것)
- 2단계(불필요한 코드 제거)에서 "미사용"으로 제거 대상이었지만, 실제로는 **사용해야 했던** 메서드
- 호출부가 존재해야 할 위치를 코드 흐름에서 추론하여 연결
- 탐색 방법: 정의만 있고 호출이 없는 메서드를 찾되, 주변 코드의 의도와 대조

### 3. 계층 간 검증 불일치
- DTO(@Valid, @Min 등)에는 검증이 있지만 Service/Entity 레이어에는 동일 검증이 없는 경우
- DTO를 거치지 않는 호출 경로(Admin 폼, 내부 서비스 호출)에서 불변식이 깨질 수 있음
- 탐색 방법: DTO 제약 조건과 Service/Entity 검증을 대조

### 4. 인터페이스 간 규칙 불일치
- 같은 비즈니스 규칙이 REST API와 Admin(MVC) 등 서로 다른 인터페이스에서 다르게 적용되는 경우
- 한쪽에서 허용하지만 다른 쪽에서 차단되어 의도대로 동작하지 않는 경우
- 탐색 방법: 동일 Service 메서드를 호출하는 Controller들의 사전 검증 로직을 비교

### 5. 빈 catch 블록 (관찰 가능성 누락)
- 예외를 의도적으로 무시하되(`catch (Exception ignored)`), 로그조차 남기지 않아 장애 감지가 불가능한 경우
- "실패해도 계속 진행"이라는 의도는 유지하면서 로그를 추가

### 6. TODO/FIXME 주석
- 코드에 TODO/FIXME로 남아 있는 미완성 의도

## 작업 방식

### 탐색 단계
1. 위 카테고리 순서대로 대상 범위 전체를 스캔하여 누락 작동을 발견한다
2. 발견된 항목마다 **의도 근거**(왜 이것이 누락인지)를 기록한다
3. 발견 목록을 사용자에게 보고하고 승인을 받는다

### 구현 단계 (항목별 TDD 루프)
1. **Red**: 누락 작동을 검증하는 실패 테스트를 먼저 작성한다
2. **Green**: 최소한의 코드로 테스트를 통과시킨다
3. `./gradlew test` (또는 프로젝트의 전체 테스트 명령)으로 기존 테스트 통과를 확인한다
4. 한 항목을 완료한 뒤 다음 항목으로 넘어간다
5. 항목별로 커밋 메시지를 제안한다

## 의도 근거 판단 기준

다음 중 하나 이상에 해당하면 "의도가 있었지만 구현되지 않은 것"으로 판단한다:
- **대칭성**: 같은 패턴의 다른 메서드에는 해당 로직이 있음
- **선언된 제약**: DTO, 주석, 메서드명 등에 규칙이 명시되어 있지만 실제 코드에는 없음
- **정의된 도구**: 메서드/유틸이 정의되어 있지만 호출되지 않고, 호출되어야 할 위치가 명확함
- **TODO/FIXME**: 코드에 미완성 의도가 명시적으로 남아 있음

다음은 "누락 작동"이 **아닌** 것:
- 새로운 기능 제안 (요구 사항에 없는 것)
- 성능 개선, 리팩터링
- 코딩 스타일 변경

## 제약

- 기존 테스트를 비활성화하거나 삭제하지 않는다
- 기존 API의 정상 작동(응답 코드, 반환값)을 변경하지 않는다
- 누락 작동 수정 외의 구조 변경(리팩터링)을 섞지 않는다
- 각 항목 수정 후 반드시 전체 테스트 통과를 확인한다
- **작동 변경은 반드시 증거와 함께 제출한다.** 테스트가 상태 변화 또는 예외를 관찰 가능한 방식으로 검증해야 한다
