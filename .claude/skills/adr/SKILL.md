# ADR (Architecture Decision Record) 작성 가이드

ADR은 아키텍처 결정의 **맥락, 선택지, 근거**를 기록하는 문서다.
"왜 이렇게 했는가?"에 대한 답을 미래의 개발자에게 남긴다.

---

## 1. ADR 작성 조건

아래 중 **하나라도 해당**하면 ADR을 작성한다:

1. **트레이드오프 존재**: 선택지가 2개 이상이고, 각각 장단점이 있는 경우
   - 예: `@Transactional` 위치를 Service vs Repository 중 어디에 둘 것인가
2. **팀 규칙/경계 결정**: 계층 간 호출 규칙, 패키지 구조, 의존 방향 등 팀 전체에 영향
   - 예: Controller에서 Repository 직접 호출 금지
3. **테스트 전략 결정**: 어떤 수준에서 무엇을 어떻게 테스트할지 결정
   - 예: 인수테스트를 MockMvc로 할지 RestAssured로 할지

---

## 2. 파일 규칙

- **위치**: `docs/adr/`
- **파일명**: `NNNN-제목.md` (번호는 4자리, 0001부터 순차)
  - 예: `0001-service-layer-transaction-boundary.md`
  - 예: `0002-domain-validation-responsibility.md`
- **제목**: 영문 kebab-case, 결정 내용을 간결히 표현

---

## 3. ADR 템플릿

```markdown
# NNNN. 제목

## 상태

proposed | accepted | rejected | superseded by [NNNN](NNNN-제목.md)

## 컨텍스트

어떤 문제 상황에서 이 결정이 필요했는가?
현재 코드의 상태, 문제점, 제약 조건을 서술한다.

## 선택지

### 선택지 1: (이름)
- 장점: ...
- 단점: ...

### 선택지 2: (이름)
- 장점: ...
- 단점: ...

## 결정

어떤 선택지를 택했고, 핵심 근거는 무엇인가?

## 결과

이 결정으로 인해 어떤 변화가 생기는가?
코드, 테스트, 운영 관점에서 예상되는 영향을 서술한다.
```

---

## 4. 상태 흐름

```
proposed → accepted    (팀이 동의하여 채택)
proposed → rejected    (채택하지 않음)
accepted → superseded  (새 결정으로 대체됨, 대체 ADR 링크 포함)
```

---

## 5. 작성 절차

```
1. docs/adr/ 디렉토리에 다음 번호로 파일 생성
2. 템플릿에 맞춰 컨텍스트, 선택지, 결정, 결과 작성
3. 상태를 proposed로 설정
4. 커밋: docs(adr): NNNN 제목 ADR 작성
5. 결정이 확정되면 상태를 accepted로 변경
```

---

## 6. 좋은 ADR의 기준

- **컨텍스트**가 충분하여, 6개월 후 읽어도 왜 이 결정이 필요했는지 이해할 수 있다
- **선택지**가 2개 이상 나열되어 있고, 각각의 트레이드오프가 명시되어 있다
- **결정**이 명확하고, 핵심 근거가 1~2문장으로 요약되어 있다
- **결과**가 구체적이어서, 이 결정이 코드에 어떤 영향을 미치는지 알 수 있다

---

## 7. 주의사항

- ADR은 **결정을 기록**하는 것이지, 모든 설계를 문서화하는 것이 아니다
- 자명한 결정(표준 패턴 적용 등)은 ADR로 남기지 않는다
- ADR을 수정하지 말고, 새 ADR로 **supersede** 한다
- 커밋과 ADR을 함께 포함하지 않는다 — ADR은 별도 `docs` 커밋으로 분리
