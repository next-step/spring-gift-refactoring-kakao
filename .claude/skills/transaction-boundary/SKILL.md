# 트랜잭션 경계 세우기

## 목표
여러 저장 작업이 하나의 논리 작업이라면, 중간 실패에서 부분 반영이 발생하지 않도록 트랜잭션 경계를 설정한다. 외부 호출이 트랜잭션을 불필요하게 점유하지 않도록 분리한다.

## 대상 범위
`src/main/java/` 아래의 모든 `@Service` 클래스

## 점검 항목

아래 카테고리를 순서대로 전체 대상 범위에서 점검한다.

### 1. 누락된 @Transactional
- 여러 Repository 쓰기(save/delete)를 수행하는 메서드에 `@Transactional`이 없는 경우
- 읽기 전용 메서드에 `@Transactional(readOnly = true)`가 없는 경우

### 2. 외부 호출과 트랜잭션 분리
- 외부 API 호출(HTTP 클라이언트, 메시지 전송 등)이 `@Transactional` 메서드 안에 있으면 DB 쓰기와 분리를 검토한다
- 외부 호출이 느리거나 실패할 때 트랜잭션이 불필요하게 열려 있는 상태를 제거한다
- 분리 방법: 외부 호출을 트랜잭션 밖으로 이동하거나, DB 쓰기 부분만 별도 트랜잭션 메서드로 추출

### 3. 부분 반영 가능성
- 하나의 논리 작업에서 여러 엔티티를 변경하는데, 중간 실패 시 일부만 반영될 수 있는 경우
- 예: 재고 차감 + 결제 처리 + 주문 저장처럼 전부 성공하거나 전부 실패해야 하는 경우

## 작업 순서
1. 대상 범위의 모든 Service 클래스를 스캔하여 점검 항목에 해당하는 메서드를 식별한다
2. 각 메서드의 현재 상태, 문제, 조치를 정리하여 사용자에게 보고한다
3. 승인 후 한 Service씩 수정한다
4. 각 수정 후 전체 테스트(`./gradlew test`)가 통과하는지 확인한다
5. 기존 작동(API 응답, HTTP 상태 코드)이 유지되는지 검증한다
6. Service별로 커밋 메시지를 제안한다

## 제약
- 기존 API 응답, HTTP 상태 코드, 작동을 변경하지 않는다
- 새로운 엔드포인트나 기능을 추가하지 않는다
- 테스트를 비활성화하거나 삭제하지 않는다
- best-effort 패턴(외부 알림 전송 실패 허용 등)이 있으면 유지한다
