# Refactor Skill

기존 분석 보고서를 기반으로 코드 리팩터링을 수행하고, 작업 결과를 분석 보고서와 README.md에 반영하는 스킬이다.

## 리팩토링이란

리팩토링은 다음 문제를 해결하는 것이다:

- **변경이 가능한 상태로 만들었는가** — 코드를 안전하게 수정할 수 있는 구조인가
- **변경 시 위험을 통제할 수 있는 구조인가** — 변경의 영향 범위를 예측하고 제한할 수 있는가

### 두 가지 종류의 리팩터링

리팩터링은 성격에 따라 두 종류로 나뉘며, **반드시 분리해서 수행한다.**

#### 구조 변경 — 입력과 출력이 유지되는 변경

외부에서 관찰 가능한 동작은 그대로 유지하면서 내부 구조만 변경한다.

- 코드 이동
- 메서드 추출
- 계층 분리
- 의존성 정리
- 네이밍 정리

#### 작동 변경 — 입력과 출력이 변경되는 변경

시스템의 외부 동작이나 정책이 달라진다.

- 정책 변경
- 트랜잭션 추가
- 예외 처리 방식 변경
- 조건 로직 수정
- 기능 수정

## 핵심 원칙

1. **분석 보고서 기반 작업** — 이미 존재하는 분석 보고서의 작업 목록에서 작업을 선택한다. 새로운 보고서를 작성하지 않는다.
2. **하나의 작업 단위** — 반드시 하나의 작업만 수행한다. 새로운 작업이 필요하다고 판단되면 코드를 변경하지 않고 분석 보고서와 README.md를 업데이트한다.
3. **인수 테스트 검증 필수** — 작업 수행 전에 해당 작업이 현재 인수 테스트 시나리오로 검증 가능한지 확인한다. 테스트가 부족하면 코드 변경 전에 테스트를 먼저 추가한다.
4. **구조 변경과 작동 변경의 분리** — 하나의 작업에서 구조 변경과 작동 변경을 동시에 수행하지 않는다.
5. **문서 반영 필수** — 작업 완료 후 분석 보고서와 README.md에 결과를 반영한다.

## 작업 절차

### 1단계: 분석 보고서 읽기 및 작업 선택

기존 분석 보고서에서 다음 작업을 식별한다.

```
1. docs/ 하위의 분석 보고서 읽기
2. 작업 목록에서 미완료 작업 확인
3. 전제 조건이 충족된 작업 중 다음 수행할 작업 1개 선택
4. 선택한 작업의 변경 종류 확인: 구조 변경인지 작동 변경인지
```

### 2단계: 인수 테스트 커버리지 확인

선택한 작업이 현재 인수 테스트로 검증 가능한지 확인한다.

```
1. src/test/resources/features/ 하위의 .feature 파일 읽기
2. 선택한 작업의 영향 범위에 해당하는 시나리오 존재 여부 확인
3. 구조 변경의 경우: 변경 전후로 입력/출력이 보존되는지 검증할 시나리오가 있는가
4. 작동 변경의 경우: 변경된 동작을 검증하는 시나리오가 있는가
5. 검증 가능 여부를 판단하고, 부족한 시나리오를 식별
```

### 3단계: 테스트 보강 (필요한 경우)

2단계에서 테스트가 부족하다고 판단되면, 코드 변경 전에 테스트를 먼저 추가한다.

```
1. 부족한 시나리오를 .feature 파일에 추가
2. 필요한 Step Definition 작성
3. 필요한 Fixture, TestDataInitializer 메서드 추가
4. ./gradlew spotlessApply — 테스트 코드 포매팅
5. ./gradlew cucumberTest — 추가한 테스트가 현재 코드에서 통과하는지 확인
6. 분석 보고서에 테스트 추가 내용 반영 (해당 작업 항목의 검증 부분 업데이트)
7. README.md에 테스트 추가 작업 반영
```

테스트 작성은 acceptance-test 스킬의 규칙을 따른다.

### 4단계: 코드 변경

분석 보고서의 작업 내용에 따라 코드를 수정한다.

```
1. 작업 내용의 각 항목을 순서대로 수행
2. 항목별 변경 후 컴파일 확인
3. 전체 변경 완료 후 테스트 실행
```

### 5단계: 스타일 적용

Java 코드를 변경한 경우, 반드시 Spotless 포매터를 실행한다.

```
1. ./gradlew spotlessApply — 자동 포매팅 적용
2. ./gradlew spotlessCheck — 포매팅 위반 없음 확인
```

### 6단계: 검증

리팩터링 후 작동이 보존되었는지 확인한다.

```
1. ./gradlew cucumberTest — 인수 테스트 실행 → 통과 확인
2. 실패 시 원인 분석 후 수정
```

### 7단계: 문서 업데이트

작업 결과를 분석 보고서와 README.md에 반영한다.

```
1. 분석 보고서 업데이트:
   - 완료한 작업 항목의 검증 결과 기록 (테스트 통과 수 등)
   - 작업 중 발견된 추가 사항이 있으면 기록
2. README.md 업데이트:
   - 해당 작업 항목에 완료 체크 ([x]) 표시
   - 테스트 추가가 있었으면 해당 내용도 체크 표시
3. 작업 중 새로운 작업이 필요하다고 판단되면:
   - 분석 보고서에 새 작업 항목 추가
   - README.md에 새 작업 항목 추가 (미완료 상태)
   - 해당 작업은 수행하지 않는다
```

## 커밋 메시지 규칙

**커밋을 직접 수행하지 않는다.** 코드 변경 완료 후 커밋 메시지를 작성하여 사용자에게 전달한다. 사용자가 직접 커밋한다.

### 형식: AngularJS Git Commit Message Conventions

커밋 메시지는 한국어로 작성하되, type은 영어로 작성한다.

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **type** (영어): `refactor`, `fix`, `feat`, `style`, `docs`, `test`, `chore` 등
- **scope** (선택): 변경 대상 모듈/패키지
- **subject** (한국어): 변경 요약 (명령형)
- **body** (한국어): 변경 사유 — "왜 이렇게 변경하는가"와 선택한 접근 방식의 근거
- **footer** (선택): 관련 이슈 번호 등

### 필수 포함 내용

- 작업 목록 단위로 커밋 메시지를 작성한다
- 변경 이유가 body에 정확하게 포함되어야 한다

### 예시

```
refactor(product): ProductController 비즈니스 로직을 ProductService로 추출

Controller에 CRUD 로직이 직접 포함되어 있어 테스트 작성과 로직 변경이
어렵다. 도메인 단위로 Service를 추출하여 Controller는 요청 검증과
위임만 담당하도록 책임을 분리한다.

대안으로 메서드 단위 추출을 검토했으나, 도메인 단위 추출이 응집도와
일관성 측면에서 더 적합하다고 판단했다.
```

## 주의사항

### 절대 하지 말 것
- 새로운 분석 보고서 작성 (기존 보고서를 업데이트만 한다)
- **구조 변경과 작동 변경을 하나의 작업에서 동시에 수행** (반드시 분리)
- 한 번에 여러 작업 단위를 수행
- **직접 git commit 수행** (커밋은 사용자가 한다)

### 반드시 할 것
- 분석 보고서의 작업 목록에서 작업을 선택
- 코드 변경 전에 인수 테스트 커버리지 확인
- 테스트가 부족하면 코드 변경 전에 테스트 먼저 추가
- 테스트 추가 시 분석 보고서와 README.md에 반영
- 변경 후 인수 테스트 실행으로 작동 보존 확인
- 작업 완료 후 분석 보고서와 README.md 업데이트
- 새 작업이 필요하면 문서에만 추가하고 수행하지 않음
- 작업 목록 단위로 커밋 메시지 작성, 변경 사유 포함
- **커밋 메시지를 사용자에게 전달** (AngularJS Convention, 한국어, type은 영어)
